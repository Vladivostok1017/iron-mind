# 规则引擎与扩展边界

> 回答三件事：海军空军到底做到哪一步了、模块能不能"碰代码"、以及"万物皆模块"这条路的边界在哪。

---

## 1 现状盘点：海军与空军

先说清楚，免得你以为已经做好了。

| 能力 | 状态 | 说明 |
|---|---|---|
| 空军侦察 | ✅ 已实现 | `recon_radius` 内的敌方省，精度=精确 |
| 空军打击 | ⚠️ 只有参数 | `strike_power` 字段存在，但**没有任何系统读它** |
| 空军战损 | ❌ 未实现 | 出动架次、被防空击落，都没有 |
| 海军舰炮支援 | ❌ 未实现 | `UnitKind::Naval` 只有枚举，无行为 |
| 海军封锁/运输 | ❌ 未实现 | 同上 |
| 装甲机动优势 | ❌ 未实现 | 移动成本不分兵种 |

**这是诚实的状态**：空军只做了一半（侦察），海军等于零。

不是不想做，是因为**海军需要"水域通行图"和"舰队编成"两个新概念**，而现在的省份模型还没有海域。空军打击则需要"制空权"这个中间层。

## 2 为什么需要规则引擎

你说得对：如果模块只能填参数，那它能做的就只是"同一套玩法换个数值"。而你想让模块能定义新玩法。

现在的模块能做什么：

```json
"comms": { "preset": "courier" }      // 换参数
"kind": "air", "recon_radius": 2      // 换类型
```

不能做什么：

- 定义"山地行军的额外损耗"——这是新机制
- 定义"夜间作战士气下降"——这是新机制
- 定义"补给车被袭后前线弹药告急"——这是新机制

这些都需要"条件 + 动作"，而不仅是参数。

### 2.1 但"模块写代码"是个危险提议

如果允许模块执行任意代码：

- 确定性没了（模块可以读系统时间、做 IO）
- 安全性没了（模块可以删文件）
- 兼容性没了（引擎一升级，模块全崩）
- 调试地狱（出问题不知道是引擎还是模块）

所以正确的形态是：**模块写声明式的规则，引擎解析执行**。不是写代码，是写"契约"。

---

## 3 三层设计：原语 / 条件 / 规则

### 3.1 原语（引擎提供，模块只能调用这些）

引擎定义一组**原子操作**，覆盖所有合理的状态修改：

```rust
pub enum Primitive {
    /// 改单位兵力（百分比）
    ModifyStrength { selector: UnitSel, delta: Fixed },
    /// 改单位士气
    ModifyMorale { selector: UnitSel, delta: Fixed },
    /// 改单位补给
    ModifySupply { selector: UnitSel, delta: Fixed },
    /// 改省份归属
    SetOwner { province: u32, side: Side },
    /// 改工事等级
    ModifyFort { province: u32, delta: i8 },
    /// 生成新单位
    SpawnUnit { template: String, province: u32 },
    /// 移除单位
    RemoveUnit { selector: UnitSel },
    /// 写一条战报
    Log { text: String },
}
```

**关键约束**：模块只能调用这些，不能直接改 `World` 的字段。这样引擎始终知道发生了什么。

### 3.2 条件（可组合的谓词）

```rust
pub enum Condition {
    All(Vec<Condition>),
    Any(Vec<Condition>),
    Not(Box<Condition>),
    /// 当前省的地形
    ProvinceTerrain(Terrain),
    /// 当前单位类型
    UnitKind(UnitKind),
    /// 当前单位的将领性格阈值
    CommanderTrait { trait_name: String, above: Fixed },
    /// tick 范围
    TickRange { from: u32, to: u32 },
    /// 常量
    Always,
    Never,
}
```

### 3.3 规则

```rust
pub struct Rule {
    pub id: String,
    /// 绑定到哪个阶段钩子
    pub phase: Phase,
    /// 同一阶段内的执行顺序（小的先跑）
    pub priority: i32,
    pub condition: Condition,
    pub actions: Vec<Primitive>,
}
```

### 3.4 模块里长什么样

```yaml
rules:
  - id: armor_bogged_in_mountain
    phase: post_movement
    priority: 0
    when:
      all:
        - province_terrain: mountain
        - unit_kind: armor
    then:
      - modify_strength: { selector: current_unit, delta: -0.02 }
      - log: "装甲部队在山区行进受阻"

  - id: night_attack_morale_loss
    phase: post_combat
    when:
      all:
        - tick_range: { from: 0, to: 0 }   # 占位，将来接时段
        - has_combat: true
    then:
      - modify_morale: { selector: all_units_in_combat, delta: -0.05 }
```

这段 YAML 不难写，但有真实效果。而且它是**声明式的**——引擎能静态检查、能排序、能保证确定性。

## 4 阶段钩子

规则必须绑定到明确的时间点，否则行为不可预测。

```
pre_tick
  ├─ pre_ai
  ├─ post_ai
  ├─ pre_supply ── post_supply
  ├─ pre_movement ── post_movement
  ├─ pre_combat ── post_combat
  ├─ pre_morale ── post_morale
  ├─ pre_intel ── post_intel
post_tick
```

模块声明 `phase: post_movement`，引擎就在移动系统跑完之后、战斗之前执行这条规则。

**钩子数量要克制。** 每加一个钩子就多一处分叉，性能和可读性都会下降。第一版只留六个：`pre_supply`、`post_supply`、`post_movement`、`pre_combat`、`post_combat`、`post_tick`。

---

## 5 确定性怎么保证

规则是模块写的，但执行必须是确定的：

1. **固定求值顺序**：按 `(phase, priority, rule_id 字典序)` 排序，不依赖文件里的书写顺序
2. **禁止随机**：规则里的随机必须走引擎的 `seeded_rng(rule_id)`，不能用外部熵
3. **禁止 IO**：不能读文件、不能联网、不能取系统时间
4. **状态修改只走原语**：这样引擎能追踪每一次改动

校验器要能静态检查这四条。

## 6 "万物皆模块"的边界

这是我最想跟你说明白的一点。

### 6.1 分四层，只有后两层能完全模块化

```
┌─────────────────────────────────────┐
│ 内核 Kernel（不可模块化）             │
│ tick 循环 / 实体存储 / RNG / 哈希 / 序列化 │
├─────────────────────────────────────┤
│ 系统 Systems（可插拔，trait 化）      │
│ 补给 / 移动 / 战斗 / 士气 / 侦察      │
├─────────────────────────────────────┤
│ 规则 Rules（模块可写，声明式）        │
│ 条件 + 动作                          │
├─────────────────────────────────────┤
│ 内容 Content（模块数据）              │
│ 地图 / 单位 / 将领 / 事件 / 结局      │
└─────────────────────────────────────┘
```

### 6.2 为什么内核不能模块化

如果连 tick 循环、RNG、哈希都由模块提供，那么：

- **确定性没人担保**。模块 A 用浮点、模块 B 用哈希表遍历，回放立刻失效
- **性能无法预估**。每个 tick 都要穿过几层动态分发
- **调试失去基准**。出问题时不知道是引擎错了还是模块错了

内核是**保证**，不是**功能**。保证不能外包。

### 6.3 系统层可以模块化，但第一版不做

理论上补给、战斗都能做成 trait + 注册表，让模块替换。

但代价是：

- 引擎复杂度翻倍
- 每个系统都要定义稳定的接口
- 你会在"设计接口"上花掉比"写系统"更多的时间

**我的建议：第一版只做规则层模块化。** 等真的有第二个战役需要"完全不同的战斗模型"时，再把系统 trait 化。过早抽象是另一种形式的浪费时间。

### 6.4 规则层是性价比最高的模块化

因为它直接对应"我想让这个战役有特殊机制"这个真实需求，而且：

- 不改内核
- 不改系统
- 只在固定钩子上插一段声明

这就是你想要的"模块碰代码"的正确形态。

## 7 和 DSH 的对比

你提到 DSH 的"万物皆模块"。两者的共同点是**内核最小化 + 扩展点明确**，但有一个关键差异：

| | DSH | 本引擎 |
|---|---|---|
| 扩展单位 | 工具、技能、插件 | 规则、内容模块 |
| 扩展方式 | 代码（TypeScript/JS） | 声明式 YAML |
| 确定性要求 | 无 | **必须逐位可重放** |
| 危险操作 | 沙箱隔离 | 直接禁止（无 IO、无随机、无任意代码） |

差异的根源是：**游戏要回放**。DSH 不需要"同一次对话逐位重放"，所以可以敞开让人写代码；游戏必须能，所以只能给声明式原语。

这不是保守，是需求决定的。

## 10 一个诚实的判断

规则引擎会让模块能力上一个台阶，但它也带来三个新问题：

1. **规则冲突**：两条规则同时改一个单位的兵力，谁先谁后？→ 用 priority，但作者还是要理解
2. **调试困难**：战局不对，是引擎的错还是规则写错了？→ 需要"规则命中日志"
3. **性能**：每 tick 对所有规则求值 → 需要空间索引（只对相关单位求值）

这三条都能解决，但要花时间。

**所以我的建议是：先做第一步（最小规则引擎），跑通"一个模块用规则实现了引擎没有的机制"这个闭环。** 如果这一步顺，后面就好办；如果不顺，说明这个抽象方向有问题，改了也不心疼。

---

## 11 一句话

**内核提供确定性，系统提供机制，规则提供扩展，内容提供具体。**

四层各守本分，"万物皆模块"才不至于变成"万物皆失控"。
