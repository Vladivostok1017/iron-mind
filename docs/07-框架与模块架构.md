# 框架与模块架构

> 核心决定：**游戏本体只提供框架（引擎），每一个战役都是一个可导入的模块。**
> 首发战役（武汉会战）在这个架构下的定位是"示例模块"，不是产品本身。

---

## 1 定位转变

原来的隐含定位是"一款有武汉会战的游戏"。现在改成：

```
产品 = 引擎（框架） + 首批内容（示例模块） + 创作工具（编辑器与校验器）
```

这三样里，引擎和工具是长期资产，内容是消耗品。

**这个转变带来三个连锁判断：**

**第一，内容生产工具必须早做。** 如果内容是产品的生命力，那"能不能方便地做内容"就是第一优先级，不是收尾工作。编辑器从 M5 提前到 M2。

**第二，引擎必须对内容"无知"。** 引擎不能出现 `if scenario == "wuhan"` 这样的代码。所有战役差异都靠数据表达。这条是硬约束，违反一次就会传染。

**第三，示例模块要"教会别人怎么做"。** 武汉会战不只是给人玩的，更是给作者看的模板——它应该展示所有能力：地图、编制、派系、事件、结局、AI 配置。

---

## 2 边界：什么在引擎里，什么在模块里

这是整个架构最重要的一张表。定错了后面全乱。

| 层 | 引擎负责 | 模块负责 |
|---|---|---|
| **模拟** | tick 循环、确定性、战斗解算算法、补给算法、移动规则 | 地图数据、编制树、单位属性、参战方、时间范围 |
| **规则参数** | 参数的**解释**与**默认值** | 参数的**取值**（地形加成、损耗系数、天气影响） |
| **AI** | 决策调度、效用函数框架、LLM 网关、上下文构建器 | 将领档案、性格向量、prompt 模板、触发条件、派系规则 |
| **事件** | 事件 DSL 解释器、校验器、执行器 | 事件骨架、槽位定义、触发条件、效果类型与区间 |
| **结局** | 结局判定引擎、历史基线框架 | 结局定义、状态变量阈值、叙事调性 |
| **表现** | 渲染管线、UI 框架、交互 | 地图美术、单位图标、界面文案、本地化 |
| **叙事** | 文本组装、LLM 调用、审核 | 语言风格、术语表、叙事模板 |

**一条判断标准**：如果换一个战役需要改代码，那说明边界画错了。

**几个容易画错的地方：**

**地形原型** —— 归引擎。`ridge_line`、`pocket` 这些是**战斗解算的算法分支**，不是数据。但"这个山头属于哪个原型"是数据。所以引擎定义原型的枚举与行为，模块标注实例。

**派系** —— 归引擎（机制），模块提供派系列表与属性。引擎不知道"桂系"是什么，只知道"有一个派系，服从度 0.65"。

**事件效果类型** —— 归引擎。模块能用的效果类型必须由引擎预先定义并实现（`supply_route_shift`、`unit_readiness`…）。模块不能凭空发明效果。

**LLM prompt** —— 归模块。这是内容的一部分。引擎提供模板变量与组装逻辑，模块提供具体的 prompt 文本与风格要求。

## 3 模块能力三层

不是所有模块作者都愿意写代码。分层是必须的。

| 层级 | 能力 | 需要什么 | 覆盖谁 |
|---|---|---|---|
| **L1 数据模块** | 换地图、编制、将领、事件、结局、文案 | 只会填表 | 90% 的作者 |
| **L2 规则模块** | 调整参数、组合地形原型、自定义事件触发条件 | 会写 YAML 表达式 | 有经验的作者 |
| **L3 脚本模块** | 自定义复杂逻辑、新的事件效果 | 会写受限脚本 | 少数技术型作者 |

**关键**：L1 必须能做出完整可玩的战役。这是生态的门槛线——如果做战役必须写代码，就没有生态。

L1 能做到什么程度？看武汉会战需要什么：
- 地图：GeoJSON 导入 + 编辑器微调 ✅
- 编制：填表（层级 + 番号 + 师长 + 派系）✅
- 将领：填表 + 选性格模板 ✅
- 事件：选骨架 + 填槽位 ✅
- 结局：填阈值 ✅
- 规则参数：调默认值 ✅

**全部是填表。** 所以 L1 足够做完整战役。L3 只在想实现特殊机制时才需要。

## 4 模块格式

```
wuhan_1938.imod/
├─ manifest.yaml          # 元数据、依赖、版本约束、能力声明
├─ map/
│  ├─ map.imap            # 编译后的地图（二进制）
│  └─ source.geojson      # 源数据（可选，供他人二次编辑）
├─ scenario/
│  ├─ scenario.yaml       # 战役定义
│  ├─ oob/                # 编制树
│  └─ objectives.yaml     # 目标与结局
├─ generals/              # 将领档案
├─ events/                # 事件骨架
├─ rules/
│  └─ params.yaml         # 参数覆盖（做"手感"差异）
├─ localization/
│  ├─ zh-CN.yaml
│  └─ en-US.yaml
├─ assets/                # 图标、立绘、音效
├─ scripts/               # 可选，受限脚本
└─ README.md              # 给玩家和作者的说明
```

### 4.1 manifest 示例

```yaml
id: org.example.wuhan_1938
name: 武汉会战 1938
name_en: Battle of Wuhan 1938
version: 1.2.0
author: example
description: 1938 年 6 月至 10 月，长江中游的五个战场。
engine:
  min: 0.4.0
  max: 1.0.0          # 不含，兼容区间
content_schema: 3     # 模块格式版本
capabilities:         # 声明用到哪些能力，加载器据此校验
  - map.custom
  - oob.four_levels
  - faction.system
  - event.generated
  - ending.multi
  - ai.general_llm
dependencies:
  - id: org.example.common_1938
    version: "^1.0.0"
tags: [china, ww2, 1938, defense]
locale: [zh-CN]
```

### 4.2 三个必须做对的字段

**`engine.min/max`** —— 引擎升级不能静默破坏旧模块。加载器发现不兼容时，要明确告知"这个模块需要引擎 0.4.x，当前 0.6.0，可能不兼容"，而不是崩溃或静默降级。

**`content_schema`** —— 模块格式自身的版本。格式演进时提供迁移器（`imod migrate`），不能要求作者手工改。

**`capabilities`** —— 声明用到的能力。加载器据此提前校验，避免运行到一半才报错。

## 5 版本契约

这是平台化最容易出问题的地方。三条规则：

**规则一：引擎对模块只增不改。** 一旦某个数据字段被发布，就不能改语义，只能新增字段。旧字段保留到下一个大版本。

**规则二：模块格式变更必须提供迁移器。** 作者用 `imod migrate --to 4` 一条命令升级，不用读 changelog 手工改。

**规则三：模块必须能锁定引擎版本。** 玩家可以选"用当前引擎运行"或"用模块推荐版本运行"（如果引擎保留了兼容层）。

**反例**：某次更新把 `strength.value` 从"人数"改成"千人数"，所有旧模块的兵力瞬间差 1000 倍。这种事发生一次，生态就死了。

## 6 作者工具链

这是生态成败的真正关键。工具链做不好，前面所有设计都是空的。

### 6.1 四件工具

| 工具 | 作用 | 什么时候做 |
|---|---|---|
| **编辑器（Editor）** | 可视化改地图、编制、事件、将领 | M2 起持续做 |
| **校验器（Validate）** | 静态检查 + 可玩性检查 + 平衡检查 | M2 |
| **预览器（Preview）** | 不加载完整游戏，快速跑 30 天看效果 | M3 |
| **打包器（Pack）** | 编译地图、压缩资源、生成 manifest | M1 |

### 6.2 校验器的三层检查

这是最有价值的工具——作者最怕的是"做完了不能玩"。

**第一层：静态校验**
- schema 合规（字段类型、必填项）
- 引用完整性（每个 `parent` 存在、每个 `commander` 有档案、每个 `neighbor` 双向）
- ID 唯一性
- 资源存在性

**第二层：可玩性校验**
- 地图连通性（无孤岛、补给可达）
- 地形原型合法性（`pocket` 必须真的三面封闭）
- 编制树完整（无空编、无循环）
- 时间与地点一致（战役期间部队能在期限内到达）

**第三层：平衡校验**
- 无头模拟跑批：同一模块跑 100 次，看结局分布
- 如果 95% 都是同一个结局 → 平衡有问题
- 如果 100% 无法结束 → 有死锁
- 输出报告：结局分布、平均结束日期、异常事件

**第三层是旗舰功能。** 它让作者能在发布前就知道"我做的这个战役好不好玩"，而不是等玩家骂。

### 6.3 一键 AI 生成（差异化功能）

既然引擎内置 LLM 网关，模块作者可以：

- `imod gen events --count 30 --tone 悲壮` → 生成 30 个待审事件骨架
- `imod gen generals --style 西北军` → 生成一批将领档案草稿
- `imod gen narrative --for ending E2` → 生成结局文案候选

生成结果**一律进待审队列**，作者逐条接受或修改。不直接入模块。

这是"AI 驱动"从玩家功能延伸到创作功能的一步。它把内容生产门槛又降了一个数量级——一个人也能做战役。

## 7 确定性边界

模块化之后，确定性不只依赖引擎，也依赖模块。三条防线：

**防线一：模块不能执行任意代码。** L3 脚本必须是受限解释器（Rhai 或 Lua 沙箱），只能调用引擎暴露的 API，不能访问文件系统、网络、随机源。

**防线二：随机数由引擎统一管理。** 模块不能自带 RNG。所有随机都用引擎的 `seeded_rng(stream_id)`。

**防线三：模块数据必须可序列化。** 模块在运行时不产生引擎无法追踪的状态。

**校验器要能检测**：脚本是否调用了禁用 API、是否引入了未声明的随机源。

## 8 分发与生态

### 8.1 分发形态

**只做本地。** 一个 `.imod` 文件（或目录），拖进游戏，或点"导入模块"选文件。分享方式是压缩包、网盘、论坛链接。

**明确不做**：在线模块中心、账号系统、评分体系、依赖自动解析、付费分成。

三个理由：

1. **非商业项目，没有运营能力也没有必要。** 平台需要持续的人力投入和审核，个人项目撑不住。
2. **审核压力。** 一旦有官方托管，历史叙事内容的责任就落到托管方。本地分发时责任在作者与玩家之间。
3. **技术收益低。** 依赖解析、版本冲突处理、增量更新——这些是平台级工程量，对"发出去给人玩"这个目标贡献很小。

代价是模块发现性差（玩家得自己去论坛找）。这个代价对个人项目可以接受。

### 8.2 加载顺序与冲突

```
引擎内置基础包（规则默认值、地形原型、效果类型）
   ↓
依赖包（如"1938 中国战场通用数据"）
   ↓
战役模块（武汉会战）
   ↓
用户补丁（改名、调参数）
```

同名 ID 冲突时，后加载的覆盖，但**必须在日志里记录覆盖链**，并在校验时报出来。静默覆盖是 bug 温床。

### 8.3 前向兼容

玩家做的东西，标准是"引擎升级后不用改就能跑"。做不到的时候，至少让作者知道改哪儿。

## 9 对路线图的影响

内容平台化让编辑器从收尾工作变成了主线工作。这是最大的调整。

| 阶段 | 原计划 | 调整后 |
|---|---|---|
| M0 | 引擎地基 | 不变（确定性 + 渲染） |
| M1 | 战斗 + 移动 | 加 **模块加载器 + 打包器** |
| M2 | 武汉会战 | 武汉会战改为**示例模块**，加**最小编辑器**（地图 + 编制） |
| M3 | AI 将领 | 加**预览器**（30 天快跑） |
| M4 | 事件与叙事 | 事件/结局全部走模块化，加**一键生成** |
| M5 | 地图导入 | 编辑器补全（事件、将领、结局的可视化编辑） |
| M6 | 打磨 | 加**校验器三层**、模块中心（可选） |

**总工期增加约 1.5 个月**，主要是编辑器与校验器。

但这是必要投入：**如果内容是产品的生命力，那内容工具就不能是最后的 10%**。很多"框架 + 内容"的游戏死在没有工具上——玩家想做内容，发现要做内容得读源码，就放弃了。

## 10 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **项目周期过长导致烂尾** | 致命（个人项目第一杀手） | 先做 3-4 个月垂直切片验证核心假设；切片不通过就不扩展 |
| 编辑器沦为半成品 | 致命（生态起不来） | 编辑器与引擎同仓、同期开发；M2 就必须能做出可玩模块 |
| 模块格式频繁变更 | 高（作者流失） | 严格遵守"只增不改"；变更必带迁移器 |
| 历史内容审核压力 | 中（非商业，压力低于商业项目） | 纯本地分发，不做官方托管与推荐；模块自带"用户创作"声明 |
| 模块质量参差 | 中 | 校验器 + 作者自测报告；不做评分体系 |
| 引擎对内容产生隐性依赖 | 中（架构腐化） | 代码评审硬性规则：不出现战役名常量 |
| 确定性被脚本破坏 | 中 | 沙箱 + 禁用 API + 校验器检测 |

### 一条必须提前说的

**审核责任。** 一旦有了模块生态，玩家可以做出任何历史叙事——包括歪曲史实、美化侵略、敏感政治表达。

技术上我们只做校验，不做内容判断。但**必须有的机制**：
- 模块声明内容类型与敏感标记
- 本地加载时提示"此模块为用户创作，不代表官方立场"
- 不做官方托管与推荐（这条在非商业定位下更彻底）
- 保留"一键屏蔽某作者/某模块"的能力

对个人非商业项目，这条的实际压力比商业项目小得多——只要不做托管、不做推荐位，就不构成"传播"。但**引擎内置的示例模块仍然是你的署名作品**，那部分的内容责任跑不掉，所以 `01` 文档里的三条红线依然要守。

---

## 11 一句话

引擎回答"这类仗怎么打"，模块回答"这一仗在这打"。

只要你换一个战役时动的是数据而不是代码，这个架构就是对的。
