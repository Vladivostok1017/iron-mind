# 情报系统与单位类型

> 解决两个问题：**你不是上帝**，以及**为什么将领不会无脑听话**。

---

## 1 三层信息模型

```
L0 真实状态        只有模拟核心知道。所有单位的真实位置、兵力、士气。
     ↓
L1 情报视图        每方一份。由侦察生成，有误差、会过期。
     ↓
L2 将领认知        将领只知道自己辖区附近的情报，不是全图。
```

玩家看的是 L1，将领决策用的是 L1（局部切片），战斗结算用 L0。

**这条边界是整个"第一人称"体验的地基。** 如果玩家能看到 L0，将领性格、侦察投入、兵力估算全部失去意义。

---

## 2 侦察来源与精度

| 来源 | 精度 | 覆盖 |
|---|---|---|
| 战斗接触 | 精确 | 同省交战的敌军，番号与规模全暴露 |
| 航空侦察 | 精确 | 空军单位半径内的敌方省 |
| 邻接观察 | 近似（±40%） | 己方地面单位相邻的省 |
| 传闻 | 只知有敌，规模不明 | 更远处由情报部门推断 |
| 未知 | 完全不知道 | 其余区域 |

**衰减**：任何情报超过 3 天没有新来源，精度降一级，直到变回未知。

这一条让侦察成为**持续投入**而不是一次性开图。你不派侦察机出去，前线的情报就会烂掉。

## 3 将领基于情报决策

AI 的所有判断（打不打、打谁、要不要撤）都读取 `enemy_estimate`，不是真实兵力。

后果是真实的：
- 情报不足时，将领可能把重兵当成空省，一头撞上去
- 也可能因为把空省当成重兵而迟疑，错失战机
- 侦察机因此有了价值——它直接改变将领的判断

这是"信息不对称"从概念变成玩法的关键一步。

## 4 将领为什么不会无脑听话

### 4.1 一个必须写下来的洞察

用 LLM 驱动将领时有个天然陷阱：**大模型经过 RLHF 训练，倾向服从"用户的要求"**。如果把"要不要抗命"交给模型判断，它几乎永远会说"服从命令"。

所以架构上必须反过来：

| 环节 | 谁做 | 理由 |
|---|---|---|
| 会不会抗命 | **引擎的确定性规则** | 必须真的发生，不能靠模型自觉 |
| 为什么抗命 | LLM | 这是叙事，不是判定 |
| 抗命后怎么打 | 引擎 | 同上 |

**判定与叙事分离**，这是让"将在外"真的能发生的前提。

### 4.2 两层决策

```
统帅部：给方向（邻接有敌省就下令进攻，不管兵力够不够）
   ↓
将领：解释这道命令
   ├─ 服从
   ├─ 打折扣（劣势时按下不动）
   └─ 自主主张（按自己的判断改目标）
```

把"上级"和"将领"拆开之后，才有了"上级要打、我按兵不动"的空间。之前两者是同一套逻辑，将领永远跟自己的判断一致，抗命概率为零。

### 4.3 独立思考

将领不是等命令的机器人。他有自己的主张：

- 好战 + 看到弱敌 → 主张主动出击
- 谨慎 + 处于劣势 → 主张按兵不动

如果主张与上级命令不同，且他的"自主性"够强（`(1-obedience) × initiative`），就按自己的想法来。

三种产物，都进战报：

```
兵力不足，未敢强攻          ← 消极抗命
战机可乘，本官自作主张      ← 主动改变
未奉撤退之命，死守此地      ← 拒绝撤退
```

### 4.4 三条硬约束

1. 将领只能改方向，不能改阵营——永远不会投敌。
2. 抗命只会朝"更保守"或"更激进"偏，不产生无意义动作。
3. 服从度 1.0 的将领永不抗命。

**这三条保证"将在外"是可玩的，不是随机的。** 玩家能逐渐摸清每个将领的脾气，并据此调整部署——这才是策略。

## 5 单位类型

| 类型 | 是否占省 | 是否地面战斗 | 特殊 |
|---|---|---|---|
| 步兵 `infantry` | 是 | 是 | — |
| 装甲 `armor` | 是 | 是 | 机动强（待实现） |
| 空军 `air` | **否** | **否** | 侦察半径、打击强度 |
| 海军 `naval` | 否 | 否 | 舰炮支援（待实现） |

空军与海军不参与地面消耗战，也不占领省份。它们提供的是：

- **空军**：侦察（`recon_radius`）、对地打击（`strike_power`）
- **海军**：舰炮支援、封锁水道（后续）

**为什么空军不能参战**：一个飞行团不是一支守备部队。如果让它参与地面战斗结算，会出现"飞机在城里跟步兵互耗"的荒谬结果。

---

## 6 对界面（未来前端）的要求

1. **只渲染 L1**：地图上显示的是"已知的敌军"，不是全部敌军。
2. **精度要可见**：用不同的符号或透明度区分精确/近似/传闻。
3. **过期要提示**：情报超过 3 天，界面要标"情报陈旧"。
4. **将领的话要能读**：抗命理由必须出现在战报里，玩家才知道"为什么这支部队没动"。
5. **侦察资产要有专门视图**：侦察机的覆盖范围、剩余航程。

## 7 还没做的

| 项 | 说明 |
|---|---|
| 将领的局部视野 | 目前将领能看到整方的情报，应该再按辖区裁剪 |
| 情报欺骗 | 佯动、假阵地、无线电静默 |
| 海军 | 只有类型定义，没有行为 |
| 装甲的机动优势 | 只有类型定义，移动规则未区分 |
| 空军的出动架次与损失 | 目前是常数强度，没有战损 |

---

## 8 一句话

**信息不对称不是折磨玩家，是让"侦察"和"判断"变成真正的决策。**

如果玩家能看见一切，那将领性格就只是表演；只有当玩家也不知道对面有多少人时，"派不派侦察机"和"信不信这个将领"才是值得做的选择。

## 9 跨时代兼容：能力声明 + 参数化

### 9.1 问题

如果引擎要支持 1805 年的骑兵传令、1938 年的有线电报、1944 年的无线电与雷达，最直接的做法是：

```rust
if era == Era::Napoleonic { ... }
else if era == Era::WW2 { ... }
```

这条路会在第三次扩展时崩掉。加一个新战役就等于改一次引擎，而且每个分支都要测试。

### 9.2 正确做法

**引擎只认机制，模块只认参数。**

```
引擎：通信延迟是一个数，侦察是一个半径与精度
模块：延迟是几天，半径是几跳
```

引擎代码里永远不出现"1805"或"1938"。判断标准很硬：**新增一个时代的战役，引擎代码零改动。**

### 9.3 通信能力

`CommsConfig` 只有四个字段：

```rust
pub struct CommsConfig {
    pub kind: CommsKind,        // 只用于叙事，不影响计算
    pub local_delay: u32,       // 战斗接触的报告延迟
    pub adjacent_delay: u32,    // 相邻省观察
    pub air_delay: u32,         // 航空侦察
}
```

`kind` 是 `Courier` / `WireTelegraph` / `Radio` / `FieldTelephone`，**只影响战报里怎么写**（"骑兵来报" vs "电台通报"），不参与任何计算。计算只看三个延迟数字。

模块里这样配：

```json
"comms": { "preset": "wire_telegraph" }
```

或者完全自定义：

```json
"comms": { "local_delay": 0, "adjacent_delay": 2, "air_delay": 3 }
```

### 9.4 各时代的建议参数

| 时代 | preset | local | adjacent | air |
|---|---|---|---|---|
| 1805 | `courier` | 1 | 3 | —（无航空） |
| 1916 | `wire_telegraph` | 0 | 2 | 2 |
| 1938 | `wire_telegraph` | 0 | 1 | 1 |
| 1944 | `radio` | 0 | 1 | 0 |

**同一条战线、同一支部队，只改这张表，游戏手感就完全不同。** 1805 年的玩家下达命令后，要等三天才知道结果；1944 年的玩家几乎当天就能看到。这不是靠写两套逻辑，是靠配两个数。

### 9.5 侦察与情报能力

侦察同样参数化：

| 能力 | 引擎实现 | 模块配置 |
|---|---|---|
| 骑兵侦察 | 半径 1，精度=近似 | `recon_radius: 1` |
| 航空侦察 | 半径 N，精度=精确 | `recon_radius: 2` + `air_delay` |
| 雷达 | 固定设施，只报"有来袭" | 未实现 |
| 无线电截获 | 不定位置，只报"有大规模通讯" | 未实现 |

**未实现的能力必须显式降级，不能静默假装工作。** 模块声明了引擎不认识的能力时，加载器给出警告，然后按"没有这个能力"运行。

### 9.6 向前兼容的三条规则

**规则一：未知能力降级，不崩溃。**

```rust
"comms": { "preset": "quantum_entanglement" }   // 引擎不认识
```
→ 退回默认值 + 警告，游戏照跑。

这是模块生态能长期存活的前提。一旦引擎遇到未知配置就崩，作者就不敢用新特性。

**规则二：显式数值覆盖预设。**

```json
"comms": { "preset": "wire_telegraph", "adjacent_delay": 5 }
```
→ 延迟 5 天，其他按预设。

作者可以只改自己关心的那一项，不用抄全套。

**规则三：能力缺席等于该能力不存在。**

如果模块没配 `comms`，用默认（有线电报）。如果没配侦察，就没有侦察——不是"用默认侦察"。

**"没写"和"写了 0"必须是两种语义。**

### 9.7 新增能力的流程

假设以后要加"雷达"：

1. 引擎加 `ReconKind::Radar` 和对应行为（固定设施、只报来袭）
2. 地图数据加"雷达站"标记
3. 模块声明 `"recon": ["radar"]`
4. **旧模块零改动**，因为它们没声明雷达

这就是扩展点该有的样子：**加东西不影响已有的东西**。

### 9.8 一个反例，说明为什么要这么设计

如果引擎内置了 `if has_radar`，那么：
- 1805 年的模块必须显式关掉雷达
- 每次加新能力，所有旧模块都要检查一遍
- 作者得读引擎源码才知道有什么开关

参数化的好处是：**默认值定义在引擎，差异定义在模块**。作者只需要写"我比默认多什么、少什么"。

### 9.9 边界：什么该参数化，什么不该

**该参数化**：数值、半径、延迟、权重、阈值。
**不该参数化**：算法的形状。

比如"补给按 BFS 衰减"是形状，"衰减率 0.75"是参数。前者写死在引擎，后者模块可调。

如果某个能力需要**不同的算法形状**（比如 1805 年没有"补给线"概念，只有"就地征粮"），那它不是参数问题，是新的能力，要走 9.7 的流程。

---

## 10 一句话

**引擎回答"这类机制怎么工作"，模块回答"这个时代的参数是多少"。**

只要新增一个战役不需要改引擎代码，兼容层就是对的。

## 附：番号要接触两次（P1 收尾）

情报系统本来就有延迟（在途报告）、有精度衰减、近似情报带 ±40% 误差。
缺的最后一块是**番号识别**：以前第一次战斗接触就同时给"精确"和"番号已知"，
等于跳过了整个识别过程。

现在：

| 来源 | 兵力 | 番号 |
|---|---|---|
| 战斗接触（第一次） | 精确 | 不知道 |
| 战斗接触（第二次及以后） | 精确 | 知道 |
| 航空侦察 | 精确 | 知道（飞机看得见番号旗与队形） |
| 邻接观察 | 近似（±40%） | 不知道 |

判"以前见过没有"用的是**精度**而不是 `seen_tick`——
第 0 天的 `seen_tick` 就是 0，拿它判断"接触过没有"会永远为假（踩过）。

测试见 `crates/sim-core/src/intel.rs` 的 `identity_needs_two_contacts`。
