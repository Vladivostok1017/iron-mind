# 钢心 / Iron Mind — 方向方案与技术提纲

> 代号：Iron Mind（钢心）
> 品类：AI 驱动的战役级大战略（实时暂停）
> 产品形态：**引擎 + 模块**。游戏本体只提供框架，每个战役都是可导入、可由玩家创作的模块。
> 项目性质：**个人项目，非商业**。自己开发、免费发布、不盈利。这一条影响所有排期与取舍。
> 定位一句话：**用"意图"打仗，而不是用"面板"打仗；每局历史都不一样，但每局都说得通。**

## 1. 为什么是这个方向

钢铁雄心类的核心魅力有三个：真实历史的重演与改写、宏大系统的耦合感、以及"我做的每个决定都留下痕迹"。

但它的门槛也是三个：**信息过载**（200+ 小时才摸到门）、**操作密度**（前线手操师级单位）、**反馈延迟**（决策后果几十分钟后才显现）。

"AI 驱动"如果只做成"生成随机事件文本"，那只是给老系统贴皮。真正能同时解决"更真实"和"门槛更低"的，是让 AI 承担**参谋与执行**的角色：

- 玩家给战略意图（"守住田家镇至月底"），AI 参谋把它拆成作战计划，AI 将领负责落地执行。
- 玩家从"微操 200 个师"变成"指挥 30 个将领"。指挥的量级降下来了，历史感反而上去了——因为你真的像统帅一样在权衡人、地、时。
- 每局不同的不只是数值，而是**人物的判断**：同一个薛岳，可能今天布口袋阵等日军钻，明天因为补给不济而选择放弃阵地。

这是一个真实存在的市场空位：喜欢二战与叙事的玩家很多，愿意花 200 小时学 HOI4 的很少。

### 为谁做

**首先服务中国玩家，这一点写进设计约束，不是营销口号。**

具体落地为五条：

1. **中文是原生语言，不是翻译。** 叙事、战报、将领口吻都按中文写，不留翻译腔。
2. **默认预设中国玩家最熟的历史语境。** 不需要为"第九战区是什么"做科普，但可以为"万家岭为什么重要"提供额外注解。信息密度可以高，但入口要浅。
3. **AI 供应商优先国内。** 默认推荐 DeepSeek / 通义 / Kimi 等，兼容 OpenAI 协议；国际服务商作为可选项。延迟和计费都对国内网络友好。
4. **敏感内容按国内标准从严。** 见 `01-武汉会战场景设计.md` 第 9 节的三条红线，按最严格的那条执行。
5. **发行路径先国内可及。** Steam 国区 + 国内平台，支付方式覆盖常规渠道。

代价是海外市场会慢一步。这是自觉的选择——把一个市场做透，比同时讨好两个市场更可能活下来。

## 2. 与 HOI4 的差异化定位

| 维度 | HOI4 | Iron Mind |
|---|---|---|
| 学习曲线 | 200 小时入门 | 2 小时拿下第一场战役 |
| 指挥粒度 | 师 → 军 → 集团军群，多层手动 | 意图 → 作战计划 → 将领自动执行 |
| 历史走向 | 固定国策树 + 固定事件 | 模板 + AI 生成 + 校验，走向发散但自洽 |
| 地图 | 固定位图，换地图等于换游戏 | 导入 GeoJSON / OSM / 位图 / 历史边界 |
| 失败成本 | 高，通常重开 | 确定性回放，可回溯分叉 |
| 人物 | 静态特质与技能 | 有性格向量、会做判断、会犯错 |
| 胜负判定 | 二元（灭国/被灭） | **不判胜负，给结局**：12 种互斥结局 + 历史基线对照 |
| 军内政治 | 弱（政治点数） | 派系系统：同一个命令，中央军、桂系、川军的反应都不同 |
| **内容形态** | 官方国策 + 社区 mod（但仍需读源码） | **引擎 + 模块**：战役是可导入的数据包，L1 填表就能做完整战役 |
| 内容生产 | 官方国策 + 社区 mod | 声明式 DSL，mod 作者不需要写代码 |

**核心取舍**：放弃"全球全景 1936-1945 全流程"，专注**单战役 60-180 天**的纵深体验。全球剧本作为后期内容扩展，而不是首发目标。这个取舍决定了整个工程的可控性。

## 3. 五条设计原则

**P1 模拟核心必须确定性可重放。**
没有这一条，后面的回放、分叉、平衡测试、AI 调试全部不成立。这是地基，不是优化项。

**P2 AI 分三层介入，风险与权限严格分离。**

| 层 | 职责 | 权限 | 风险 | 兜底 |
|---|---|---|---|---|
| L3 规则层 | 生成事件的效果与数值 | 只能产出"候选参数"，不能直接改世界 | 高（会破坏平衡） | DSL 校验 + 预算约束 + 无头沙盒试跑 |
| L2 决策层 | 将领/国家的作战与政策决策 | 只能在合法动作空间内发指令 | 中（会做出蠢决策） | 启发式效用函数兜底 |
| L1 叙事层 | 把结构化结果翻译成人话 | 无世界写入权限 | 低（只是文本） | 模板拼装 |

一次 AI 调用最多只能触及其中一层。L3 的产出必须经过人审或自动校验才能进事件库，永远不能实时直连世界状态。

**P3 一切 AI 输出必须落在合法动作空间内。**
将领不能"自由发挥"，只能调用游戏暴露的 typed orders（Move / Attack / Defend / Resupply / Reinforce / Fortify）。这样 AI 的错误最多是"战术失误"，不会是"系统崩溃"。

**P4 可解释性。**
每个 AI 决策必须附带 `rationale`，玩家能在战报里看到"第 7 装甲师后撤，因为补给线被切断且侧翼暴露"。没有这一条，AI 就是黑箱，玩家不会信任它，也就谈不上"指挥感"。

**P5 数据与逻辑分离。**
地图、场景、事件、将领、装备全部是数据文件。代码只负责解释数据。这是"导入配置"和"mod 生态"的前提。

**P6 不判胜负，给结局。**
历史战役的胜负无法用一个分数衡量。用状态变量 + 规则匹配出互斥的结局，不用加权求和。这一条同时解决了三个问题：史实上说得通、玩家不会被"刷分"误导、数值平衡的容错空间大一个数量级。详见 `05-结局系统设计.md`。

## 4. 可行性的关键判断（必须先想清楚的三件事）

### 4.1 将领不能每个 tick 调 LLM

粗算一下：100 个将领 × 每天一次决策 × 90 天 = 9000 次调用。每次即便只喂 2000 token 输入，也是 1800 万 token。延迟、成本、稳定性都不可接受。

**正确做法是三层降级：**

```
每 tick        → 本地效用函数（微秒级，无 LLM）
每天/每三日    → 规则化决策树（微秒级）
关键节点触发   → LLM 决策（战役转折、重大损失、政治危机、玩家质询）
```

"关键节点"由事件总线触发，一局下来通常只有几十到几百次。LLM 在这里才有价值：它处理的是**模糊的、需要权衡的、有性格色彩**的判断。

再加两条优化：
- **态势指纹缓存**：把世界状态哈希成指纹，相似态势直接复用历史决策。
- **决策周期错峰**：不同将领的决策日错开，避免同一 tick 内并发爆炸。

### 4.2 LLM 生成的内容必须被"关进笼子"

自由生成的事件九成会出问题：经济数值爆炸、逻辑矛盾（1944 年出现 1950 年的装备）、叙事与史实冲突。

**解法是"模板槽位 + 参数化效果"**，不是"直接生成事件脚本"：

- 事件骨架由设计师写死（触发条件、作用域、可选分支、效果类型）。
- LLM 只负责填两个东西：**叙事文本**，以及**受约束数值区间内的具体取值**。
- 生成结果经过：schema 校验 → 预算校验（这次事件给玩家多少资源，占全局预算的百分比）→ 无头模拟试跑（跑 30 天，看经济/战线是否异常漂移）→ 入库待审。

这套约束的价值在于：它把"AI 能不能用"从模型能力问题，变成了工程问题。即使换到能力较弱的模型，只要笼子够结实，产出依然可用——这对一个要长期运营、模型随时会换代的项目至关重要。

### 4.3 地图"真实"不等于"复杂"

真实地理数据直接转成省份，会立刻暴露三个问题：省份形状碎、边界不可读、邻接关系有孤岛。

**必须有一层"可玩性抽象"**：地理数据只作为属性来源（高程、土地覆盖、河流、铁路、城市），省份的**形状与数量**由玩法需求决定（比如单战役目标 240-320 省、每省 4-12 个邻接、每个战区 40-60 省）。

这一层抽象是地图管线的核心工作，也是最容易被低估的部分。

## 5. 目标体验与"低门槛"机制

### 5.1 一根主线：意图 → 计划 → 执行 → 复盘

1. 玩家下达**意图**："两周内夺取瑟堡，保障登陆场补给。"
2. AI 参谋生成 **2-3 套作战计划**（不同风险偏好），附预计伤亡、补给消耗、成功概率区间。
3. 玩家选一套，或修改约束（"不许动用装甲预备队"）。
4. 将领**执行**，每天汇报。玩家只处理例外：参谋标记为"需要决策"的事项。
5. 战役结束，**复盘**：你的每个意图、每次干预、将领的每次判断，对照结果。

### 5.2 四个降低门槛的具体机制

**意图式命令。** 玩家操作的单位是"任务"而不是"师"。画一个区域 + 选一个目标 + 给一个期限，剩下的交给参谋。

**每日态势简报。** 一页纸：3 条建议、1 条风险、1 条"如果你什么都不做会发生什么"。

**分项托管。** 生产、后勤、外交、情报可以逐项交给 AI 部长，玩家随时收回。新手全托管也能玩，老手全手动也行。这是同一套系统的两种用法，不是两个难度。

**战史回溯。** 确定性模拟 + 动作日志，支持回到任意一天重来。失败的成本从"重开 30 小时"变成"退回 3 天"。这直接改变了游戏的心理负担。

### 5.3 复杂度渐进

新手战役（武汉会战 70 天精简版）只开放：移动、战斗、补给、要塞、制空轰炸。
完整战役逐步解锁：派系、限期命令、疾病、工业转移、外交、情报。
**所有系统从第一天就存在于模拟核心里**，只是 UI 层逐步暴露。避免"新手版和老手版是两套代码"。

## 6. 系统架构

### 6.1 分层

```
┌─────────────────────────────────────────────────────┐
│  表现层  Renderer                                    │
│  TypeScript + WebGL (PixiJS)  地图/单位/特效/图表     │
├─────────────────────────────────────────────────────┤
│  客户端逻辑  Client Shell                            │
│  输入、相机、UI 状态机、意图编辑器、战报阅读器          │
├─────────────────────────────────────────────────────┤
│  模拟核心  Sim Core   （Rust → WASM）                │
│  固定 tick 循环 / 实体 / 系统 / 战斗解算 / 补给 / 经济 │
│  【不依赖 AI，无 AI 也能完整运行】                     │
├─────────────────────────────────────────────────────┤
│  数据层  Content                                     │
│  场景包 / 地图 / 事件库 / 将领库 / 装备表             │
├─────────────────────────────────────────────────────┤
│  AI 编排层  AI Orchestrator （Node sidecar）         │
│  上下文构建 / LLM 网关 / 工具执行 / 缓存 / 审核        │
├─────────────────────────────────────────────────────┤
│  持久化  Persistence                                 │
│  快照（二进制）+ 动作日志 + 决策日志                   │
└─────────────────────────────────────────────────────┘
```

**关键约束：模拟核心对 AI 零依赖。** AI 是"可插拔的指挥官"，拔掉它游戏照样能跑（将领退回纯启发式）。这条约束保证了：性能可控、可按需关闭、测试可隔离。

**AI 编排层是纯 HTTP 客户端。** 不做本地推理，只做：态势包构建、多 provider 适配（OpenAI 兼容协议优先，覆盖国内主流服务商）、结构化输出校验、缓存与去重、内容审核、用量计费。这样一来，换供应商只是换一个 base_url 和模型名。

### 6.2 通信与边界

| 边界 | 机制 | 频率 |
|---|---|---|
| Renderer ↔ Client | 同进程，共享内存 | 60 Hz |
| Client ↔ Sim Core (WASM) | 结构化克隆 + 共享 typed array | 命令式，非每帧 |
| Sim Core ↔ AI Orchestrator | IPC 消息（异步，不阻塞 tick） | 事件驱动，低频 |
| AI Orchestrator ↔ 云端 API | HTTPS（流式），带超时与重试 | 每局几十到几百次 |
| Sim Core ↔ Persistence | 快照序列化 | 存档/自动存档 |

AI 调用**永远异步**。tick 不等 LLM，超时就用启发式兜底，结果晚到就丢弃或记为"延迟生效"。这一条是保证帧率和可玩性的硬性规则。

### 6.3 目录结构（建议）

```
iron-mind/
├─ crates/
│  ├─ sim-core/          # 确定性模拟核心（no_std 友好）
│  ├─ sim-content/       # 数据加载与 schema 校验
│  ├─ mapgen/            # 地图管线（离线 CLI）
│  └─ sim-testbed/       # 无头模拟跑批（平衡测试）
├─ apps/
│  ├─ desktop/           # Tauri 壳
│  ├─ client/            # 渲染与 UI
│  └─ ai-orchestrator/   # AI 编排 sidecar
├─ content/
│  ├─ maps/
│  ├─ scenarios/
│  ├─ events/
│  └─ generals/
├─ mods/                 # 示例 mod 与格式规范
└─ docs/
```

## 7. 技术选型与取舍

### 7.1 推荐方案

| 层 | 选择 | 理由 |
|---|---|---|
| 模拟核心 | Rust，编译到 WASM | 性能、确定性、内存可控；同一份代码可跑无头测试 |
| 渲染 | TypeScript + PixiJS (WebGL2) | 2D 地图类游戏足够；UI 迭代速度最快；mod 工具链好做 |
| 桌面壳 | Tauri 2 | 体积小、内存低、Rust 生态一致；比 Electron 省 200MB+ |
| 数据格式 | YAML（人写）+ JSON（机器）+ 二进制（运行时） | 人可读可 diff，运行时快 |
| 缓存/索引 | SQLite | 事件库、决策缓存、存档索引 |
| AI 网关 | Node (TypeScript) | 生态成熟，各家 SDK 齐全，流式输出方便 |
| 地图管线 | Rust CLI + 可选 Web 编辑器 | 离线批处理 + 可视化微调 |

### 7.2 备选方案与放弃理由

**Bevy (Rust 全栈)**：模拟性能最好，但 UI 和地图编辑器要自己造轮子，迭代速度慢 2-3 倍。对大战略这类"UI 即游戏"的项目，这是致命伤。放弃。

**Unity**：生态好，但 WASM 支持差、确定性难保证（浮点与物理引擎不可控）、授权成本。放弃。

**Godot 4 + GDExtension**：确定性可以做到（只要不碰物理引擎），UI 也比 Bevy 好。但地图工具链和 mod 热重载要额外投入。**这是唯一值得认真考虑的替代方案**，如果团队里有人擅长 Godot，可以切换。

**纯 Web (无 WASM)**：TS 跑 800 省 × 5000 单位的天 tick 会卡。不可行。

### 7.3 一个务实的降级路径

WASM 的性能天花板大约是原生的 60-80%。如果后期发现模拟核心吃紧，迁移路径是：**同一份 Rust 代码直接编译成原生动态库**，通过 Tauri 的 IPC 调用，Renderer 不变。这个迁移成本被架构隔离在很低的水平——这正是选 Rust 写核心的价值。

## 8. 确定性模拟核心

### 8.1 确定性五件套

1. **定点数**：所有模拟数值用 `i32`/`i64` 定点（Q16.16），禁用 `f32`/`f64`。渲染层可以随便用浮点，模拟层不行。
2. **固定 tick**：1 tick = 1 游戏日，逻辑帧率与渲染帧率完全解耦。渲染插值读的是"当前 tick 与下一 tick 的插值系数"，不改写状态。
3. **有序容器**：所有遍历必须有序。用 `BTreeMap` / 索引 `Vec`，禁用 `HashMap` 迭代（除非用于查找而非遍历）。
4. **多流 RNG**：每个子系统独立 RNG 流，seed 由 `hash(world_seed, tick, system_id, entity_id)` 派生。这样一个系统加随机数不会影响另一个系统。
5. **决策日志**：所有 LLM 决策写入日志，回放时读日志而非重调。日志本身是存档的一部分。

### 8.2 状态哈希与黄金回放

每个 tick 结束计算一次世界状态哈希（可选，测试时开启）。测试用例是"固定场景 + 固定指令序列 → 固定哈希序列"。CI 里跑，任何哈希漂移立即报警。

这是防止"改了一行代码，三个战役的平衡全变了"的唯一可靠手段。

### 8.3 核心 ECS 与系统顺序

系统在一个 tick 内按固定顺序执行，顺序本身是规格的一部分：

```
1. 时间/天气推进
2. 补给网络求解（从源头沿交通网扩散）
3. 移动与接触判定
4. 战斗解算（逐战区，按前线顺序）
5. 损耗与经验结算
6. 军官伤亡与替换
7. 派系与命令结算（服从度判定、限期命令检查）
8. 经济与生产
9. 政治与外交
10. 事件触发检查
11. 情报与迷雾更新
12. AI 决策入队（异步，不阻塞）
13. 状态哈希（测试用）
```

补给放在移动之前、战斗在后——这个顺序决定了"断补给立刻掉战斗力"的因果关系，是玩法规格，不能随意调换。

第 7 步"派系与命令结算"是中国战场特有的一级系统（见 `01-武汉会战场景设计.md` 第 4 节）。它放在战斗之后、经济之前，因为它的输入是"这轮打得怎么样"，输出是"下属下一轮还听不听你的"。这个因果顺序同样不能调换。

## 9. AI 驱动子系统

### 9.1 事件系统（L3）

**流水线：**

```
触发条件命中
   ↓
从事件库检索候选骨架（向量检索 + 标签过滤）
   ↓
LLM 填充：叙事槽位 + 数值参数（约束在区间内）
   ↓
Schema 校验（字段完整性、类型、引用存在性）
   ↓
预算校验（本次事件给玩家的资源/惩罚占总预算比例）
   ↓
无头沙盒试跑 30 天（经济漂移、战线异常、死锁）
   ↓
入待审队列 → 人工/自动批准 → 进入运行时事件池
```

**事件 DSL 示例**（设计师手写骨架，LLM 只填 `{}` 部分）：

```yaml
id: log_supply_crisis_01
scope: [theater, division_group]
weight: 30
trigger:
  all:
    - supply_efficiency: { lt: 0.45 }
    - duration: { days: 5 }
    - weather: [storm, rain]
cooldown_days: 14
slots:
  narrative: {}
options:
  - id: reroute
    text: "改走南线，多耗 20% 燃油"
    effects:
      - supply_route_shift: { distance_penalty: "0.10..0.25" }  # 区间由 LLM 定
      - political_cost: { value: "0..5" }
    narrative: {}
  - id: halt
    text: "暂停进攻，等待补给"
    effects:
      - unit_readiness: { delta: "-0.15..-0.05" }
      - lose_initiative_days: "3..7"
    narrative: {}
```

注意：数值写的是**区间字符串**，LLM 只能在区间内取值。区间由设计师定义，AI 无权突破。

**成本控制**：事件库是**预生成 + 缓存**的。一局 90 天的战役，实际运行时命中最多 20-40 个事件，其余事件在打包时批量预生成。这样运行时几乎零延迟，也可以用更贵的大模型。

### 9.2 将领系统（L2）

**将领档案不是"数值面板"，是"人格 + 履历 + 偏好"：**

```json
{
  "id": "gen.xue_yue",
  "name": "薛岳",
  "portrait": "portraits/xue_yue.webp",
  "faction": "fac.central",
  "traits": ["offensive_minded", "calculating", "stubborn", "uses_terrain"],
  "vector": {
    "aggression": 0.78,
    "caution": 0.50,
    "logistics_focus": 0.45,
    "initiative": 0.85,
    "loyalty": 0.75,
    "adaptability": 0.80
  },
  "preferences": {
    "favored_terrain": ["mountain", "river"],
    "doctrine": "kill_zone_defense",
    "aversion": ["static_defense", "counterattack_into_firepower"]
  },
  "career": [
    { "year": 1938, "theater": "wuhan", "result": "wanjialing_encirclement" }
  ],
  "decision_policy": {
    "llm_enabled": true,
    "llm_triggers": ["decisive_battle", "supply_crisis", "political_order_conflict"],
    "fallback": "utility_v1"
  }
}
```

`faction` 字段是中国战场的关键。它和 `loyalty` 一起决定"这个命令会不会被真正执行"——同一个"坚守至 X 日"，中央军会执行但要求增援，桂系会执行但提政治条件，川军可能因为补给崩溃而提前瓦解。详见 `01-武汉会战场景设计.md` 第 4 节。

**决策循环：**

```
每 tick：执行既定计划（纯本地，无 LLM）
每 3 日：效用函数重新评估，可能微调
触发式：命中 llm_triggers → 构建态势包 → 请求 LLM → 校验 → 生成 Orders
```

**将领能发出的工具调用（合法动作空间）：**

```
move(units[], destination, echelon)
attack(target_region, axis, tempo)
defend(region, depth, reserve)
resupply(route_priority)
reinforce(region, source)
withdraw(units[], fallback_line)
request_authority(what)      // 向玩家/上级请示
report(message)              // 写进战报
```

每个调用返回结构化结果 + 如果被拒绝的原因（资源不足 / 越权 / 目标不可达）。LLM 看得到拒绝原因，下一轮可以自我修正。

**性格如何影响行为**：`aggression` 高 → `attack` 的效用权重大，`defend` 阈值低；`logistics_focus` 低 → 忽略补给警告的容忍度更高。**向量直接影响效用函数的权重**，LLM 只处理"效用在几个方案间差不多、需要人味判断"的情况。这样即使 LLM 不可用，将领也依然"像他自己"。

### 9.3 参谋与副官

**每日态势简报**（1 页，固定模板 + LLM 润色）：

```
【第 17 天 · 1944-06-23 · 阴，能见度差】
形势：瑟堡外围已破，但第 7 军补给仅够 4 日。
建议 1：暂缓东进，优先打通 N13 公路。（代价：延缓 5 天）
建议 2：请求第 1 步兵师接管侧翼。（风险：正面变薄）
风险：德军第 2 装甲师疑似向北调动，情报置信度 60%。
若不动：补给效率将在第 21 天降至 30% 以下。
```

三条建议来自**效用函数的 top-3 候选**，LLM 只负责把它们写成人类能读懂的话。这样建议一定"有理有据"，不会瞎编。

### 9.4 上下文构建器（工程重点）

LLM 拿不到游戏的全部状态（token 装不下）。需要一个**态势压缩器**：

```
输入：完整世界状态（~10^5 个字段）
输出：≤ 1500 token 的态势包

组成：
  - 当前目标与约束（来自玩家意图）      ~150 token
  - 时间/位置/天气/能见度               ~100 token
  - 麾下单位摘要（只给异常值与关键值）    ~500 token
  - 敌情（含置信度，不撒谎）            ~250 token
  - 补给与后勤                          ~200 token
  - 最近 7 天的事件与结果                ~300 token
```

**压缩策略的核心是"只报异常"**：单位满编满补就不提，只提掉到阈值以下的。这一条比任何 prompt 技巧都省 token。

对手 AI 也一样，且**必须保留情报不确定性**——给 LLM 的敌情带置信度，它才知道该侦察。

### 9.5 叙事层（L1）

战报、无线电、报纸、战地日记。这层可以**完全离线预生成**，运行时只做检索和拼接。成本几乎为零，效果稳定。

这一层的价值常被低估：它是"历史感"的主要来源，而且是唯一可以放心让 AI 自由发挥的地方。

## 10. 地图与历史数据管线

### 10.1 输入源分层

| 层 | 数据源 | 用途 | 许可 |
|---|---|---|---|
| 地形基底 | SRTM / Copernicus DEM | 高程、坡度、通行性 | 公有领域 / 开放 |
| 土地覆盖 | ESA WorldCover | 森林、农田、城市、沼泽 | CC-BY |
| 水系 | HydroSHEDS / OSM waterway | 河流、渡口、洪泛区 | 开放 |
| 行政/城市 | Natural Earth / GADM | 城市位置、人口权重 | 公有领域 / 非商业注意 |
| 历史国界 | CShapes 2.0 | 按年份的国界 | 学术许可 |
| 交通网 | OSM + 历史铁路图（人工整理） | 铁路、公路、港口 | ODbL |
| 手工校准 | 设计师标定 | 胜利点、要塞、机场 | 自有 |

**HOI4/EU4 地图导入**：只做**格式解析器**（用户提供自己拥有的文件），不分发任何原始资源。这是社区常见做法，但法律边界必须写清楚。

### 10.2 处理链

```
原始数据
  ↓ 投影到战役区域（等距圆柱 / Lambert）
  ↓ 网格化：Voronoi（基于城市/地形特征点）或六边形网格
  ↓ 省份属性聚合：高程均值、坡度、土地覆盖占比、河流穿越
  ↓ 交通网叠加：铁路/公路 → 省间连接权重
  ↓ 城市与胜利点：人口加权 + 手工校准
  ↓ 补给图构建：从补给源沿交通网的可达性与容量
  ↓ 可玩性抽象：合并碎省、拆分大省、保证邻接度
  ↓ 校验器
  ↓ 输出 map.imap + 缩略图 + 场景绑定
```

**可玩性抽象的硬指标**（写进校验器）：

- 省份数在目标区间（战役级 200-800）
- 每省邻接数 4-12（少于 4 是走廊，多于 12 是碎块）
- 无孤岛（所有省从补给源可达）
- 无单省国家（除非设计如此）
- 每个战役目标至少有 2 条进攻路线（避免单点卡死）
- 补给源到前线的最长补给链 ≤ 12 跳

### 10.3 工具形态

- **CLI**：`mapgen build --source region.geojson --target provinces=600 --out map.imap`
- **可视编辑器**：Web 页面，直接读写 `map.imap`，支持画省界、改属性、跑校验、看补给热力图
- **一键导入**：玩家给一个 GeoJSON + 一个时间点，生成可玩的战役骨架

最后这个"一键导入"是整个项目的宣传点，也是最有传播力的功能。

## 11. Mod 与内容格式

### 11.1 包结构

```
mymod.imod/
├─ manifest.yaml          # 元数据、依赖、版本约束
├─ map/                   # 可选，覆盖地图
├─ scenario/              # 场景定义
├─ events/                # 事件骨架
├─ generals/              # 将领档案
├─ equipment/             # 装备表
├─ localization/          # 多语言
└─ scripts/               # 可选，受限的脚本扩展
```

### 11.2 三个必须做对的地方

**版本化 schema + 迁移器。** 每个数据文件带 `schema_version`，加载器内置向上迁移。否则一次更新会杀掉所有 mod。

**冲突检测与加载顺序。** 同名 ID 的冲突要在加载时报出来，不能静默覆盖。给作者一个 `imod check` 命令。

**热重载。** 改事件 YAML 不重启游戏就能看到效果。这直接决定 mod 作者的迭代速度，进而决定生态规模。

### 11.3 脚本的边界

允许受限脚本（Lua 或 Rhai）处理复杂条件，但**禁止脚本访问模拟核心的内部可变状态**，只能调用暴露的查询与动作 API。否则确定性无法保证，也没有安全边界。

## 12. 关键接口示例

### 12.1 模拟核心 → AI（态势包）

```rust
pub struct SituationPacket {
    pub tick: u32,
    pub date: GameDate,
    pub theater: TheaterId,
    pub objective: Objective,
    pub weather: Weather,
    pub own_units: Vec<UnitBrief>,      // 只包含异常与关键单位
    pub enemy_estimate: Vec<EnemyBrief>, // 每项带 confidence: u8
    pub supply: SupplyBrief,
    pub recent_events: Vec<EventBrief>,
    pub authority: AuthorityBounds,      // 该将领能做什么、不能做什么
    pub token_budget: u16,
}
```

### 12.2 AI → 模拟核心（指令）

```rust
pub enum Order {
    Move { units: Vec<UnitId>, to: RegionId, echelon: Echelon },
    Attack { target: RegionId, axis: Axis, tempo: Tempo },
    Defend { region: RegionId, depth: u8, reserve: Vec<UnitId> },
    Resupply { priority: Vec<RouteId> },
    Withdraw { units: Vec<UnitId>, fallback: RegionId },
    RequestAuthority { what: String },
}

pub struct OrderEnvelope {
    pub order: Order,
    pub rationale: String,     // 必填，进战报
    pub confidence: u8,
    pub issued_at: u32,
}
```

`Order` 进入模拟核心后，先过**合法性校验器**：越权、资源不足、目标不可达、单位已被歼灭，全部拒绝并回传结构化原因。

### 12.3 LLM 工具契约（发给模型的 JSON Schema 片段）

```json
{
  "name": "issue_order",
  "description": "向麾下部队下达一道命令。只能在授权范围内行动。",
  "parameters": {
    "type": "object",
    "required": ["order_type", "rationale"],
    "properties": {
      "order_type": { "enum": ["move", "attack", "defend", "resupply", "withdraw", "request_authority"] },
      "target": { "type": "string", "description": "目标区域 ID，必须来自态势包" },
      "units": { "type": "array", "items": { "type": "string" }, "maxItems": 12 },
      "tempo": { "enum": ["cautious", "normal", "aggressive"] },
      "rationale": { "type": "string", "maxLength": 200 }
    }
  }
}
```

约束要点：`target` 和 `units` 必须来自态势包中出现的 ID（防幻觉），`maxItems` 限制指挥规模，`rationale` 强制要求——它同时是战报素材和调试线索。

## 13. 性能与容量预算

| 指标 | 目标 | 备注 |
|---|---|---|
| 省份数 | 240-320（单战役）/ 8000+（全景，后期） | |
| 同时活跃单位 | 3000-5000 | 师级 |
| 模拟 tick | 1 日 / tick，单 tick < 8 ms (WASM) | 300 省基准 |
| 渲染 | 60 fps @ 1440p | |
| 内存 | < 1.2 GB | Tauri + WASM |
| 存档 | < 15 MB | 快照 + 日志（压缩后） |
| 冷启动到可玩 | < 8 s | |
| LLM 调用（一局 90 天） | 50-300 次 | 关键节点触发 |
| LLM 成本（云端 API，一局 120 天） | < ¥15 | 关键节点触发 + 预生成 |
| AI 决策延迟容忍 | < 2 s（异步），超时降级 | 绝不阻塞 tick |

### 13.1 纯 API 方案的成本模型

已确定不做本地模型（小模型判断质量不足以支撑将领决策）。全部走云端 API，因此成本控制成了架构约束，而不是优化项。

**四道闸门：**

1. **预生成优于实时调用。** 事件库、战报模板、报纸、无线电台词，全部在打包时批量生成并缓存。运行时只做检索与拼接。这一条把 80% 的调用量挪到了开发期，运行时近乎零成本。
2. **分级模型。** 日常将领决策、态势简报用便宜模型；战役转折、重大历史节点、需要人味的判断用强模型。按调用点分档，不按玩家分档。
3. **额度硬上限。** 每局设定 token 预算，接近上限时自动降级到启发式，并在 UI 上明示"AI 参谋已离线"。宁可少 AI，不可账单失控。
4. **玩家自带 Key。** 玩家填入自己的 API Key（支持多家国产与国际服务商），成本直接由玩家承担；官方只提供默认推荐与用量预估。这是纯 API 方案最现实的分发形态。

**Key 处理的硬要求**：本地加密存储（Windows DPAPI / macOS Keychain），只在 AI Orchestrator 进程内解密，不进日志、不进存档、不出现在任何 UI 文本里。

**降级链**：主 API 超时或限流 → 备用 API → 启发式效用函数 → 纯规则模式。整条链上，游戏永远可玩，只是"人味"递减。

## 14. 里程碑路线图

假设：1 人全职，或 4-5 人小团队。

| 阶段 | 周期 | 目标 | 验收标准 |
|---|---|---|---|
| **M0 引擎地基** | 6 周 | WASM 核心 + 地图渲染 + 确定性回放 | 同一输入两次运行状态哈希完全一致；300 省地图 60fps |
| **M1 战斗与模块** | 10 周 | 省份、师、移动、战斗解算、补给网络；敌方规则 AI；**模块加载器 + 打包器** | 一次 70 天纯 AI 对战能跑完不崩；能加载一个外部编写的极简模块 |
| **M2 示例模块 + 最小编辑器** | 11 周 | 武汉会战精简版存为**独立模块**；编辑器能改地图、编制 | 人类玩家用"意图"打完一局并看到结局；用编辑器把示例模块改出新战役 |
| **M3 AI 将领与派系** | 9 周 | L2 上线，将领配置全部走模块；加**预览器**（30 天快跑） | 玩家能分辨薛岳与汤恩伯；预览器 3 分钟内看出一局大致走向 |
| **M4 事件、结局与生成** | 8 周 | 事件与结局全部模块化；一键 AI 生成（事件/将领/文案） | 一局出现 20+ 个事件；`imod gen events` 能产出可用的候选 |
| **M5 地图导入与编辑器补全** | 10 周 | GeoJSON/OSM 导入；事件、将领、结局的可视化编辑 | 导入陌生区域，15 分钟内产出可玩战役 |
| **M6 校验器与打磨** | 10 周 | 三层校验器（静态/可玩/平衡）、教程、性能、本地化 | 20 名外部玩家无引导完成首局；作者能在发布前看到结局分布 |

**两处调整需要说明：**

**M1 多了"敌方 AI"和"模块加载器"。** 前者因为只做中方可玩，日方必须是对手；后者因为模块化是产品形态，不是后期功能。

**M2 从"做战役"改成"做示例模块 + 最小编辑器"。** 这是平台化最关键的一次转向：如果 M2 结束时作者还得读源码才能改内容，那生态的路就是断的。编辑器必须和第一版内容同时出现。

合计约 13-15 个月。**建议在 M2 结束后（约 8 个月）做一次"要不要继续"的决策点**——那时引擎能跑、模块能装、编辑器能用，核心假设（意图式指挥是否好玩、模块是否真的可做）都已被验证。

### 如果是个人业余项目（现实排期）

上面的 13-15 个月是按全职算的。业余投入（每周 10-15 小时）意味着 **3-4 年**，这个周期几乎必然烂尾。

所以个人项目不该照着上面走，而应该先做**垂直切片**：

**目标：3-4 个月，做出一个能玩完整一局的粗糙版本。**

| 项 | 切片版做什么 | 砍掉什么 |
|---|---|---|
| 引擎 | 确定性 tick、省份、师、移动、战斗、补给 | 事件、结局叙事、派系、疾病 |
| 地图 | 一条战线（南浔线德安—万家岭），约 60 省 | 五条战线全图、历史交通网精细数字化 |
| 数据 | 手写 YAML，不做编辑器 | 编辑器、校验器、预览器 |
| AI | 纯规则（效用函数），不接 LLM | 将领性格、LLM 决策 |
| UI | 地图 + 部队图标 + 简单面板 | 战报、简报、意图编辑器 |
| 结局 | 只判"武汉陷落日期"一项 | 12 种结局 |

**为什么砍到这么少**：切片要回答的只有一个问题——**"意图式指挥"到底好不好玩**。这个问题不需要编辑器、不需要 LLM、不需要叙事，只需要能下意图、AI 能执行、结果可读。

如果这个切片不好玩，所有后续投入都是浪费。如果好玩，再按完整路线图扩展。

**这也是"引擎 + 模块"的第一次自我验证**：切片的地图如果必须手写在代码里才能跑，说明模块化没做对；如果能从 YAML 读进去，架构就立住了。

### 首作战役：1938 武汉会战（精简版）

完整场景设计见 `01-武汉会战场景设计.md`。选它的理由与诺曼底不同：

- **五条战线天然并行**，共享一个预备队池。玩家最核心的决策是"预备队押哪条线"，这正好是意图式指挥最能发挥的场景，而不是靠减少操作量硬凑。
- **不判胜负，给结局。** 武汉最终失守，但中方达成了迟滞、保存兵力、工业转移三个战略目标。结局系统能表达这种"丢了城但打赢了战略"的复杂结果，而且不需要完美平衡数值。
- **中国战场的派系政治**（中央军 / 桂系 / 川军 / 西北军）是欧洲战场没有的一级系统。同一个命令，不同派系反应不同，这正是 LLM 最擅长、也最有戏的部分。这也是整个项目最强的差异化。
- 时间 120 天，一局 6-10 小时，节奏可控。

**M2 只做两条线**（江北线广济—田家镇 + 南浔线德安—万家岭），70 天，6-8 个军对 3-4 个师团。用最小范围验证"预备队调度"这个核心假设。

替代序列（按推荐度）：1944 诺曼底（地理数据最易获取，可作为第二个战役）→ 1942 阿拉曼 → 1941 巴巴罗萨局部。

## 15. 风险清单

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| LLM 生成破坏平衡 | 高 | 致命 | 模板槽位 + 预算约束 + 沙盒试跑 + 人审；LLM 无权突破数值区间 |
| AI 决策不可控/不可预测 | 中 | 高 | 合法动作空间 + 效用函数兜底 + 全量日志 |
| LLM 延迟拖垮体验 | 中 | 高 | 全异步、超时降级、预生成缓存；绝不阻塞 tick |
| **API 依赖风险**（限流、涨价、下线、区域不可用） | 高 | 高 | 多 provider 适配层 + 自动降级链 + 玩家自带 Key；核心体验不建立在单一供应商上 |
| **API 成本失控** | 中 | 中 | 每局 token 硬上限 + 分级模型 + 预生成；接近上限即降级并明示 |
| 确定性被无意破坏 | 高 | 高 | 定点数 + 有序容器 + 黄金回放 CI；架构上隔离 |
| 地图数据版权 | 中 | 法律 | 只用开放许可数据；HOI4 类文件只做解析不内嵌 |
| **中国战场史料数字化程度低** | 高 | 中 | 战斗序列（OOB）规模可控，手工录入；地形/水系用国际开放数据；关键数据双源交叉验证 |
| **史观与内容审查** | 高 | 致命 | 三条红线写进设计规格（战争罪行不可作为效率工具、不美化侵略、不消费苦难）；AI 内容白名单 + 人工复核 |
| **派系系统难以平衡** | 中 | 中 | M2 只做三个派系、三个参数（服从度/补给优先级/意志）；不做全套政治系统 |
| 范围膨胀（想做全球全景） | 高 | 致命 | 首发锁定单战役；全景放到 v2 |
| WASM 性能天花板 | 中 | 中 | 架构已隔离，可切原生动态库 |
| "AI 生成"变成廉价卖点被玩家反感 | 中 | 中 | 卖点讲"指挥体验"不讲"用了 AI"；AI 失败时体验不降级 |

最后一条尤其重要：**不要把它当成 AI 游戏来营销**。玩家关心的是"我终于能像将军一样打仗了"，不是"这个游戏有 LLM"。AI 是手段，是隐形的。

## 16. 决策记录

已拍板：

- ✅ **AI 部署**：纯云端 API（不做本地模型）。架构简化为 HTTP 客户端 + 多 provider 适配 + 降级链，详见 13.1。
- ✅ **首作战役**：1938 武汉会战（精简版两条战线起步），详见 `01-武汉会战场景设计.md`。
- ✅ **胜负判定**：不判输赢，给结局。12 种互斥结局 + 历史基线对照，详见 `05-结局系统设计.md`。
- ✅ **阵营**：只做中方可玩，日方全部由 AI 控制。数据与内容生产力全部集中在中方。
- ✅ **产品形态**：引擎 + 模块。游戏本体只提供框架，每个战役都是可导入的模块，玩家可自行创作。详见 `07-框架与模块架构.md`。
- ✅ **项目性质**：个人项目，非商业，免费发布。不设商业模式、不做付费内容、不做在线平台。
- ✅ **地图归属**：引擎内置全球底图（低精度，仅用于选战役与坐标参考），战役地图由模块携带（聚合属性，2-8 MB）。详见 `04` 第 10 节。
- ✅ **排期策略**：先做 3-4 个月的垂直切片验证核心假设，再按完整路线图扩展。

待拍板：

1. **平台**：PC 优先（推荐，Windows 单平台起步）/ Web 优先（传播好但性能受限）/ 双端。
2. **切片范围**：南浔线单线（推荐，60 省）/ 江北线 / 两条线一起。
3. **是否从第一天就接 LLM**：切片段先纯规则（推荐）/ 一开始就接。

## 17. 一句话总结

先做一个**确定性战役模拟器**，再给它装上**会思考但被关在笼子里的参谋与将领**，最后用**可导入的真实地图**让每一局都能复现你熟悉的那片战场。顺序不能反：先有可靠的模拟，AI 才有意义。

而第一个战场选武汉，是因为它同时提供了三件别处很难凑齐的东西：五条并行且互不相救的战线、一份不够用的预备队、以及一群各有立场、不会无条件服从的将领。

最后是形态：**这一切都要能被别人复制。** 如果只有官方能做出战役，这个项目就是一个战役；如果作者用编辑器就能做出自己的战役，它才是一个平台。所以引擎从第一天起就要对内容"无知"，编辑器从第一版内容起就要能用。

判断标准只有一条：**换一个战役时，动的是数据还是代码。**
