# 结局系统设计

> 替代"胜负判定"。不定输赢，给结局。
> 核心判断：历史战役的"胜负"本身就无法用一个分数衡量，而"结局"可以。

---

## 1 为什么不做胜负判定

三个理由。

**第一，史实本身就不支持二元判定。** 武汉会战，中方丢了武汉，但达成了迟滞、保存兵力、工业转移三个战略目的。你说这算赢还是输？如果算输，那"以空间换时间"的国策就是错的；如果算赢，那丢掉的武汉算什么。这个问题在史料里争论了几十年，一个游戏没资格替它下结论。

**第二，加权求和的分数会诱导玩家"刷分"。** 一旦显示总分，玩家就会去优化那个数字，而不是去思考"我该怎么打这一仗"。这恰恰背离了"意图式指挥"的初衷。

**第三，分数无法表达"代价"。** 用 20 万人的伤亡换 10 天时间，和用 3 万人的伤亡换 10 天时间，总分可能一样，但这是完全不同的两场仗。分数掩盖了这种差别。

所以：**不判胜负，给结局。** 结局是"历史会怎么记住这一仗"，不是"你赢了还是输了"。

---

## 2 三层结构

```
状态层：记录一局结束时的客观状态（不是分数）
   ↓
规则层：用布尔条件组合匹配结局（不是加权求和）
   ↓
叙事层：为匹配到的结局生成"战史评价"（LLM，L1 层，低风险）
```

关键区别：**加权求和是分胜负，规则匹配是给结局。** 前者把所有维度压成一个数，后者保留每个维度的意义。

---

## 3 状态变量

一局结束时记录以下状态。这些是"事实"，不是"分数"。

| 变量 | 类型 | 说明 |
|---|---|---|
| `wuhan_fall_date` | 日期 \| null | 武汉陷落日期；null 表示未陷落 |
| `wuhan_status` | enum | 完整 / 部分失守（仅汉口或汉阳）/ 全失 |
| `divisions_kept` | 比例 | 战役结束时可用师数 ÷ 战前师数（按战斗力加权，不是简单计数） |
| `industry_moved` | 比例 | 工业设备转移完成度（对应宜昌大撤退） |
| `cn_casualties` | 人数 | 中方伤亡 |
| `jp_casualties` | 人数 | 日军战斗伤亡 |
| `jp_sick` | 人数 | 日军病员（非战斗减员） |
| `international` | 0-1 | 国际观感（外媒报道、租界反应、援华力度） |
| `home_front` | 0-1 | 后方稳定度（民心、士气、政治压力） |
| `commanders_lost` | 列表 | 阵亡的将领 |
| `key_terrain_lost` | 列表 | 失守的要塞与隘口 |
| `faction_collapse` | 列表 | 溃散的派系部队 |
| `lines_held` | 整数 | 五条战线中，到最后仍在有效抵抗的条数 |
| `player_interventions` | 计数 | 玩家干预次数（用于对比历史基线） |

**注意 `divisions_kept` 的算法**：不是数师的数量，是按"剩余兵力 × 战斗力系数"加权。一个满编中央军师和一个残破川军师，价值差三倍。这个细节决定了结局的合理性。

## 4 结局谱系

不是二元的，是一个谱。从最好到最坏，加上几个特殊的。

| ID | 结局名 | 触发条件（核心） | 调性 |
|---|---|---|---|
| **E1** | 天炉 | 武汉未失守，且日军伤亡 > 中方伤亡 × 0.4 | 极少见。真正打赢了 |
| **E2** | 以空间换时间 | 陷落于 10/25 之后，主力保存 > 70%，工业转移 > 80% | 历史线的最优解 |
| **E3** | 苦撑待变 | 陷落于 10/10—10/25，主力保存 55-70% | 常态，撑住了但代价大 |
| **E4** | 僵持 | 武汉仅部分失守，双方在外围长期对峙 | 谁也没赢，但守住了核心 |
| **E5** | 换血 | 陷落于 10 月，主力保存 < 55%，但日军伤亡惨重 | 两败俱伤 |
| **E6** | 中枢崩解 | 某条战线被中央突破，导致三条以上战线同时溃退 | 崩盘 |
| **E7** | 速溃 | 陷落于 9/15 之前 | 失败 |
| **E8** | 弃守之议 | 玩家主动弃守武汉，主力保存 > 85% | 争议。保存了力量，但政治上难交代 |
| **E9** | 独木难支 | 三个以上派系部队溃散或拒不执行命令 | 派系叙事 |
| **E10** | 死守成仁 | 武汉未失守，但主力保存 < 40% | 悲壮。赢了战役，输了本钱 |
| **E11** | 国际转折 | 坚持 > 120 天，且国际观感 > 0.7 | 特殊。引发外部介入 |
| **E12** | 人心向背 | 后方稳定度 < 0.3，无论军事结果如何 | 特殊。军事之外的失败 |

### 4.1 判定优先级

结局必须互斥，否则玩家会看到自相矛盾的评语。用优先级顺序匹配，第一个命中即停：

```
1. E6 中枢崩解     （崩盘优先于一切，因为这是最显著的结果）
2. E9 独木难支     （派系崩解同理）
3. E12 人心向背    （后方崩溃是根本性的）
4. E7 速溃         （过早失守）
5. E1 天炉         （打赢了）
6. E10 死守成仁    （打赢了但打光了）
7. E4 僵持         （没丢核心）
8. E8 弃守之议     （主动放弃）
9. E11 国际转折    （特殊外交路线）
10. E2 以空间换时间（历史最优）
11. E3 苦撑待变    （常规）
12. E5 换血        （代价过大）
13. E_default      （兜底，不该触发）
```

**为什么 E11（国际转折）排在 E2 前面**：如果玩家达成了国际介入，那这个结果比"守住/没守住"更有历史意义。这是一个"隐藏结局"，值得优先呈现。

### 4.2 规则的可读性

每个结局的触发条件必须能被玩家理解。所以判定后要展示"为什么是这个结局"：

```
【以空间换时间】
✓ 武汉陷落于 10 月 28 日（晚于历史 3 天）
✓ 主力保存 78%（历史约 65%）
✓ 工业转移完成 85%（历史约 80%）
✗ 日军伤亡未达"天炉"门槛
```

这个"判定依据"面板比分数有用得多——它告诉玩家"我做对了什么、还差什么"。这是重玩动机的来源。

## 5 结局呈现

每个结局不是一句"你赢了"，而是四块内容：

**1. 标题与评级**
如"以空间换时间 · 上"（评级是评价等级，不是胜负）。

**2. 战史评价（200-300 字，LLM 生成）**
根据玩家的实际数据写，不是套模板。要求引用具体数字和事件：

> 六月至十月，你以十四个集团军、近百万之众，在长江两岸三百公里的正面上顶住了日军九个师团。武汉终究没能守住，但你把它拖到了十月末——比日军自己的时间表晚了整整一个月。更要紧的是，二十个师的老兵留了下来，宜昌码头的设备运走了八成半。这些数字在当时的报纸上不会出现，但它们决定了此后七年的战争还能不能打下去。

**3. 历史对照（固定内容）**
告诉玩家真实历史是什么样：

> 史实：武汉于 1938 年 10 月 25 日弃守。中方投入近 100 万，伤亡 25 万余；日军投入约 35 万，伤亡 3 万余（不含病员）。重庆方面的战略判断是"以空间换时间"，这一判断在此后数年被证明是正确的。

**4. 因果链（游戏生成）**
列出玩家的关键决策如何导向这个结局：

> 关键节点：
> - 8 月 24 日 你把第 25 军押在江北，瑞昌因此提前失守，但田家镇多守了 11 天
> - 9 月 17 日 你拒绝了张自忠"放弃潢川"的请求，第 59 军在此后 5 天损失过半
> - 10 月 6 日 你从大别山抽调两个军南下万家岭，促使薛岳完成了合围

这一块是整个系统的灵魂——它把"结局"和"玩家的具体行为"连起来，让玩家感到"这一仗是我打的"。

## 6 历史基线对照

每局开始时，系统会在后台跑一次"历史基线"：用 AI 自动操作，走一条接近史实的路线。结束时，把玩家的结果和历史基线并排显示。

```
              历史基线        你的战局
武汉陷落      10月25日        10月28日  (+3天)
主力保存      64%             78%       (+14%)
工业转移      80%             85%       (+5%)
中方伤亡      25.1万          22.3万    (-2.8万)
日军伤亡      3.0万           3.8万     (+0.8万)
```

这个对照表解决了"我怎么知道我做得好不好"的问题，而且**不需要任何分数**。玩家自己就能看出来：我多撑了三天，少死了三万人，多运走了百分之五的设备。

它还有一个好处：历史基线是"标准答案"的一种表达，但玩家可以偏离——偏离本身就是叙事。

## 7 AI 在结局系统里的角色

严格限定在 L1（叙事层），**不参与判定**。

| 环节 | 谁做 | 理由 |
|---|---|---|
| 状态记录 | 模拟核心 | 客观事实 |
| 结局判定 | 规则引擎 | 必须确定、可复现 |
| 战史评价文案 | LLM | 需要人味，可接受不确定性 |
| 因果链梳理 | 规则引擎 + LLM 润色 | 事实由引擎给，文笔由 LLM 给 |
| 历史对照 | 固定内容 | 不允许 AI 改动史实 |

**LLM 的输入**是一个结构化摘要（状态变量 + 关键事件列表 + 匹配到的结局 ID），**输出**是一段 300 字以内的评价。约束：

- 不得添加未发生的事件
- 不得评价政治立场
- 不得使用"胜利""失败"这类二元判断词
- 必须引用至少三个具体数字

这四条约束让结局文案既能出彩，又不会胡说。

## 8 实现要点

**1. 结局定义是数据，不是代码。**
```yaml
# content/scenarios/wuhan_1938/endings.yaml
- id: E2
  name: 以空间换时间
  priority: 10
  conditions:
    all:
      - wuhan_fall_after: 1938-10-25
      - divisions_kept: { gt: 0.70 }
      - industry_moved: { gt: 0.80 }
  tone: 坚韧、克制、肯定但不庆祝
  rating: 上
  narrative_seed: 迟滞成功，代价可控
  history_note: 史实：武汉于1938年10月25日弃守……
```

**2. 条件求值器必须确定性。** 和模拟核心共用同一套定点数与日期比较逻辑。

**3. 未命中任何结局时不能崩。** 有兜底结局，并记录日志（这是设计漏洞的信号）。

**4. 结局可以"部分达成"。** 允许 E3 的玩家看到"你差 3% 就够到 E2 了"——这种提示比直接给高分更有驱动力。

**5. 结局解锁记录。** 本地保存"已解锁结局"，给重玩动机。但不做成就系统，不做攀比。

---

## 9 这套设计对平衡的影响

这是最实际的收益：**不需要完美平衡数值了。**

传统设计里，如果一个策略太强，玩家会一直赢，游戏失去张力。所以必须把数值调到"刚好能赢"。

结局系统里，任何策略都对应一个结局。太保守 → E8 弃守之议；太激进 → E10 死守成仁；均衡 → E2/E3。**每个选择都有它的评价，但没有"正确答案"。**

这让数值设计的容错空间大了一个数量级，也让玩家愿意尝试不同的打法——因为每种打法都有它自己的结局值得一看。
