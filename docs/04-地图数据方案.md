# 地图数据方案

> 回答一个问题：1938 年武汉会战的战场地图，数据从哪来、怎么变成可玩的省份。
> 结论先说：**瓶颈不是找不到数据，而是没人做"历史交通网手工数字化"这一层。** 这层工作量约 2-3 周/战役，且它本质上是设计工作，不是数据工程。

---

## 1 整体思路：四层管线

不要指望"下载一个 1938 年中国地图文件"。不存在，也不可能有——1938 年的中国没有可用的数字地图。

正确做法是分层拼装：

```
L3 历史形态修正   ← 考据，修正湖泊/河道/城市范围/战场要点      （最费人力）
L2 历史交通与聚落 ← 手工数字化 1938 年的铁路、公路、城镇         （瓶颈所在）
L1 历史制图参考   ← 公有领域扫描图，作为 L2 的描图底稿          （免费、可靠）
L0 现代自然地理   ← 地形、水系、海岸线、土地覆盖                （免费、可靠）
```

L0 和 L1 是"拿",L2 和 L3 是"做"。整个地图管线的成本 90% 在 L2+L3。

---

## 2 L0：现代自然地理（拿）

自然地理在两万平方公里、八十七年尺度上的变化，远小于人文地理。除了湖泊围垦和河道整治，山、丘陵、水系骨架基本不变。所以这一层可以直接用现代开放数据。

| 数据 | 来源 | 分辨率 | 许可 | 用途 |
|---|---|---|---|---|
| 高程 | SRTM v3 / Copernicus DEM | 30m | 公有领域 / 开放 | 坡度、通行性、山区判定 |
| 水系 | HydroSHEDS | 15-500m | 开放 | 河流、流域、渡口候选点 |
| 海岸/湖泊 | Natural Earth 1:10m | 1:10m | 公有领域 | 大尺度水域轮廓 |
| 土地覆盖 | ESA WorldCover | 10m | CC-BY | 森林、农田、湿地、建成区 |
| 湖泊水面 | OSM water | 矢量 | ODbL | 湖区精确轮廓（需修正） |

**注意事项：**
- 鄱阳湖 1938 年的面积远大于现在（20 世纪大规模围垦）。L0 拿到的现代湖岸线只能作为"下限"，必须用 L3 修正。
- 长江中游在 1938 年有多处自然弯曲，后来被裁弯取直。对玩法影响不大，但对"渡口位置"和"航道"有影响，需要修正关键几处。
- OSM 的 ODbL 许可有传染性：如果地图数据是从 OSM 衍生的，衍生数据也要 ODbL。建议只把 OSM 当参考，最终几何自己生成（加权 Voronoi 的结果不构成 OSM 衍生作品）。

## 3 L1：历史制图参考（拿）

这是最被低估的资源。1930-40 年代，美国军方和日军都对中国做了大规模地形测绘，这些图大部分已经数字化，且多为公有领域。

| 资源 | 内容 | 获取 | 许可 |
|---|---|---|---|
| **美国国会图书馆（LOC）地图部** | 美国陆军地图局（AMS）中国系列，1:25万 为主，1940 年代 | https://www.loc.gov/maps/ | 美国政府作品，公有领域 |
| **日本国立国会图书馆** | 日军测绘中国地图，1:5万 / 1:10万 | 国立国会图书馆数字馆藏 | 日本政府文件，多数公开 |
| **亚洲历史资料中心（JACAR）** | 日军作战地图、兵要地志 | https://www.jacar.archives.go.jp/ | 公开，逐项确认 |
| **普林斯顿大学地图馆** | 中国铁路图、民国交通图 | maps.princeton.edu | 视具体图幅而定 |

**用法**：这些扫描图作为 QGIS 里的栅格底图（配准后），在其上描线。不是直接使用图本身（分辨率、版权都有限制），而是**用它来定位 1938 年的铁路线、公路、村落位置**。

**注意事项**：
- 谭其骧《中国历史地图集》有版权，只能作为参考阅读，不能复制图件。
- 上世纪 50 年代中国测绘的 1:5万地形图大部分未公开，不要指望。
- 日军地图的"公开"不等于"可商用"，如果需要商用，逐幅确认或只用其几何信息（坐标点）而不复制图像。

## 4 L2：历史交通与聚落（做，瓶颈）

这是整个地图管线的核心工作。1938 年的中国没有全国公路网，铁路只有几条干线，绝大多数运输靠水运和人力。把这个状态准确表达出来，恰恰是这个游戏"真实感"的来源。

### 4.1 战区内需要数字化的要素清单

**铁路（约 6 条，共约 700 公里）**
- 平汉铁路南段（信阳—汉口）
- 粤汉铁路北段（武昌—岳阳，作为后方补给线）
- 南浔铁路（九江—南昌，南昌方向）
- 浙赣铁路西段（南昌—萍乡，远端）
- 淮南铁路（合肥方向，远端）
- 京汉线北段（仅作为背景，不进入战区）

**公路（约 10-15 条）**
1938 年的公路多为土路，雨天不可通行。主要：
- 汉宜公路（汉口—宜昌）
- 汉黄公路（汉口—黄陂—麻城）
- 鄂东公路（黄冈—浠水—蕲春—广济）
- 南浔公路（九江—德安—南昌）
- 瑞武公路（瑞昌—武宁）
- 信潢公路（信阳—潢川—商城）
- 其他联络线

**航道（约 5 条）**
- 长江主航道（九江—武汉—宜昌段，含枯水/汛期差异）
- 汉水（汉口—襄阳方向）
- 鄱阳湖入江水道
- 赣江（南昌方向）
- 洞庭湖—湘江水道（远端）

**聚落（约 200-300 个点）**
- 武汉三镇（汉口、武昌、汉阳）
- 战区级城市：九江、瑞昌、德安、广济、黄梅、蕲春、阳新、大冶、信阳、潢川、商城、麻城、黄陂、孝感、咸宁、蒲圻
- 县级城镇：约 40 个
- 乡镇与村落：约 200 个（只在"战场要点"附近需要精确）

### 4.2 工作量估算

| 要素 | 数量 | 单人耗时 |
|---|---|---|
| 铁路线描图 | 6 条 / 700km | 3 天 |
| 公路线描图 | 12 条 / 900km | 4 天 |
| 航道 | 5 条 | 2 天 |
| 城镇定位 | 250 个点 | 3 天 |
| 战场要点（山头、村落、要塞、渡口） | 80-120 个 | 5 天 |
| 湖泊/河道修正 | 鄱阳湖、长江故道、马口湖等 | 3 天 |
| 校验与修正 | — | 3 天 |

**合计约 3 周**，单人，熟悉 QGIS 的情况下。如果只想做 M2 的两条战线（江北 + 南浔），可以压到 8-10 天。

### 4.3 工具链

```
QGIS（配准、描图、属性录入）
  → 导出 GeoJSON
  → mapgen CLI（Rust）：投影、网格化、聚合成省份
  → .imap（二进制，运行时加载）
  → Web 编辑器（微调省份边界、属性）
```

QGIS 是标准选择，免费、跨平台、支持栅格配准（把扫描地图对齐到经纬度）。描图时把 L1 的扫描图作为底图，直接画。

## 5 L3：历史形态修正（做，考据）

这一层决定"像不像 1938 年"。

| 需要修正的东西 | 依据 | 影响 |
|---|---|---|
| 鄱阳湖 1938 年湖岸线 | 历史地理研究、民国地图 | 决定水网阻断的范围，直接影响马当—湖口战线的通行性 |
| 长江中游故道与浅滩 | 航道志、水文资料 | 影响舰船通行与渡口选择 |
| 马口湖、武山湖、赤湖等中小湖泊 | 民国地形图 | 影响田家镇要塞的侧翼 |
| 1938 年城市建成区范围 | 民国地图 | 影响巷战判定，武汉三镇的范围远小于现在 |
| 花园口决堤后的黄泛区（背景） | 史料 | 约束日军能否沿平汉线南下 |
| 汛期水位（6-8 月） | 水文站历史记录 | 影响水网与渡口，是重要的季节机制 |

**重点**：鄱阳湖这一项必须查证。围垦前它的水面比现在大得多，而这直接决定"马当要塞能不能被绕过"。

## 6 从数据到可玩省份

### 6.1 算法选择

**推荐：加权 Voronoi + 后处理合并。**

理由：
- 六边形网格规整、好看，但省份形状会失去"地形感"，丘陵和山口无法自然形成走廊
- 纯 Voronoi 会产生大量碎省和锯齿边界
- 加权 Voronoi（种子点权重按聚落规模、地形特征分配）能兼顾"自然"和"可控"

流程：

```
种子点集（聚落 + 地形特征点 + 手工锚点）
   ↓ 加权 Voronoi 剖分
初始省份
   ↓ 合并碎省（面积 < 阈值 或 邻接 > 上限）
   ↓ 沿地形线修边（山脊、河流作为天然边界）
   ↓ 属性聚合（高程、坡度、土地覆盖、交通、水系）
   ↓ 邻接图构建 + 连通性校验
   ↓ 补给图求解
   ↓ 战役要点标注（手工）
   ↓ 输出 .imap
```

### 6.2 校验器的硬指标

这些必须写进自动化校验，不通过不让发布：

- 省份数在 240-320
- 每省邻接数 3-12
- 无孤岛（所有省从补给源可达）
- 每个战役目标至少 2 条进攻路线
- 补给源到前线最长链 ≤ 10 跳
- 水域省份必须与陆地省份有渡口连接
- 要塞省份必须有至少 2 个方向可攻

### 6.3 分区与层级

```
战区（Theater，5 个）
  └─ 战役区（Sector，约 15-20 个）
       └─ 省份（Province，240-320 个）
            └─ 地形节点（Terrain Node，可选，80-120 个）
```

地形节点指张古山、万家岭、富金山这类"一个省内的高地"。M2 阶段不做战术层，地形节点只作为属性（防御加成、视野），不进入独立战场。

## 7 备用方案：如果历史数据来不及

如果 L2/L3 的历史数字化拖慢进度，可以用"现代地图 + 历史约束"的降级方案：

1. 先用现代 OSM/地理数据生成省份（2 天能出图）
2. 用历史史料标注"哪些路当时不存在"（铁路清单、公路开通年份）
3. 用参数化的方式表达不确定性（比如"该区域道路密度为低"而不是精确画线）

**代价**：地形会偏现代（路网太密、湖泊偏小）。**收益**：M2 能提前 2 周跑起来。

建议：M2 用降级方案先跑通玩法，M5 再补历史精度。不要把地图精度和玩法验证绑在一起。

## 8 法律与合规

| 数据类型 | 可用性 | 注意事项 |
|---|---|---|
| SRTM / Copernicus DEM | 可自由使用 | 署名即可 |
| Natural Earth | 公有领域 | 无需署名（但建议署名） |
| HydroSHEDS | 开放 | 遵守其引用要求 |
| OSM | ODbL | 衍生数据需同样许可；建议只做参考 |
| 美国军方地图（LOC） | 公有领域 | 可自由使用与改编 |
| 日本军方地图 | 多数公开 | 商用需逐项确认 |
| 民国时期地图出版物 | 视出版者 | 中国境内出版物可能仍在版权期 |
| 谭其骧《中国历史地图集》 | 有版权 | 只读参考，禁止复制图件 |
| HOI4 / EU4 地图 | 受版权保护 | **只做格式解析，不分发任何原始资源** |
| 游戏内截图/视频 | 受版权保护 | 不作为数据源 |

**红线**：不复制任何受版权保护的地图图件。允许的做法是"参考其信息，自己重新绘制几何"。坐标点（比如某个村落在东经 115.3 度）是事实，不受版权保护；地图的图形表达受版权保护。

## 9 一个务实的判断

地图这一块最容易出现的错误，是把"历史精度"当成目标本身。

对游戏来说，玩家能感知的是：
- 这条线为什么守不住（因为两侧是湖，正面太窄）
- 为什么绕不过去（因为中间是山，只有一条隘口）
- 为什么补给断了（因为铁路被切断了）

**他感知不到"这个省的边界和 1938 年的县界差了三公里"。**

所以精度只要支撑"因果可读"就够了。把省界做到测绘级，是浪费；把"隘口、渡口、湖汊、铁路"这四个东西做准，游戏就真实了。

这也是为什么 L2 的 100 个战场要点，比 L3 的精确湖岸线更重要——前者决定玩家能不能读出"这里为什么是咽喉"，后者只影响地图好不好看。

## 10 地图的归属：引擎给什么，模块给什么

这是模块化架构下的核心问题。一句话回答：

> **坐标系统归引擎，地图内容归模块。引擎内置一张粗糙的全球底图，模块携带自己那块的精修地图。**

### 10.1 为什么不是"一张全球地图"

直觉上会想"内置一张地球地图，所有战役都在上面"。这条路走不通，原因不是数据量，是**省份划分不能共用**。

武汉会战的 300 个省，边界按 1938 年的地形、交通、战场要点划分；换成诺曼底，同样是 300 个省，但边界完全不同。全球统一划分？那武汉区域会被切成 50 个省，太粗，打不出"每个山头反复易手"的密度。

**所以省份划分必然是战役级的，地图也必然是模块级的。**

### 10.2 三层结构

| 层 | 内容 | 归属 | 体积 |
|---|---|---|---|
| **G0 全球底图** | 海岸线、国界、主要水系、粗地形 | **引擎内置** | 10-30 MB |
| **G1 战役地图** | 省份多边形、地形属性、交通网、地形节点 | **模块携带** | 2-10 MB |
| **G2 可选高精数据** | 战区地形纹理、卫星影像、原始 DEM | 可选数据包 | 50 MB-2 GB |

**G0 全球底图**：用 Natural Earth 1:110m 或 1:50m（公有领域）。它只做三件事：世界视图、选战役区域、提供坐标参考。**不含省份**。

**G1 战役地图**：这是模块的核心资产。关键是——**它不携带原始 DEM，只携带聚合后的属性**。

这是容易被忽略的一点。一个省需要的只是：

```yaml
province:
  elevation_mean: 320     # 米，DEM 聚合结果
  elevation_max: 780
  slope_mean: 0.42        # 0-1
  landcover: { forest: 0.6, cropland: 0.3, urban: 0.1 }
  river: true
  lake: false
```

原始 DEM 是 400km × 400km 的 30m 栅格，约 1.8 亿个点、700 MB。但聚合到 300 个省之后，只剩几千个数值。**从 700 MB 降到 3 MB。**

所以模块地图很小，可以直接塞进压缩包。

**G2 可选高精数据**：如果玩家想要真实地形纹理（而不是色块），单独下载。引擎支持按需加载，没有也能玩（用色块渲染）。

### 10.3 体积估算

| 内容 | 规模 | 体积 |
|---|---|---|
| 全球底图（Natural Earth 1:110m） | 全地球 | ~10 MB |
| 全球底图（Natural Earth 1:50m） | 全地球 | ~30-50 MB（简化后） |
| 战役地图（300 省，含属性与邻接） | 400×400 km | 2-5 MB |
| 战役地图 + 地形节点 + 交通网 | 同上 | 4-8 MB |
| 地形纹理（可选，2048×2048） | 战区 | 20-40 MB |
| 全球战役地图（8000 省） | 全球 | 40-80 MB |

**结论：全球高精度地图不是数据问题。** 8000 个省的地图也就几十 MB。

### 10.4 那为什么不做全球战役

数据能装下，但**没有人做过"把全球切成 8000 个可玩省"这件事**，而且每个区域的地形、交通、城市、历史归属都要考据。

具体工作量：按武汉会战 3 周/区域算，全球约 40-60 个可玩区域 → **2-3 年纯地图工作**。

所以正确的路线是：

```
引擎内置全球坐标系 + 粗糙全球底图
   ↓
每个战役区域做成一个模块（3 周/个）
   ↓
"全球战役" = 把 20 个区域模块叠起来玩
```

这样全球战役不需要一次性做完，玩家可以自己加区域模块。**模块化本身就解决了全球化的成本问题。**

### 10.5 技术契约

引擎和模块之间必须约定四件事，否则模块地图装不进引擎：

**1. 坐标系**：一律 WGS84 经纬度存储，渲染时按模块声明的投影转换。

```yaml
map:
  bbox: [113.0, 28.5, 117.5, 32.5]    # 西/南/东/北
  projection: china_lcc                # 兰勃特等角圆锥，适合中纬度东西向战区
  grid: voronoi_weights                # 生成方式，供编辑时重算
```

**2. 省份 ID**：全局唯一，格式 `{module_id}:{本地索引}`。跨模块引用（比如一个战役引用另一个模块的地形）时有意义。

**3. 邻接对称性**：A 的邻接里有 B，B 的邻接里必须有 A。校验器强制检查。

**4. 边界闭合**：多边形首尾点相同，且不自交。这是渲染和邻接计算的前提。

### 10.6 引擎内置的全球底图干什么用

不是没有意义的。它做四件事：

1. **选战役**：世界地图上圈出战区
2. **战略视图**：把战役缩到全球尺度看（比如"武汉失守对全局的影响"）
3. **坐标参考**：模块地图的边界校验（不能超出地球）
4. **未来拼接**：多个区域模块在同一张底图上拼成"大战场"

第 4 条是关键——**它让模块化的战役能拼起来，这才是全球战役的正确实现方式**。

> 这些不是史料，是**设计资产**——把"历史上这仗为什么这么打"翻译成可复用的地图与关卡结构。

## A.1 七条战略走廊

地图骨架不是省份集合，是走廊。所有战役都发生在走廊上，走廊之间的山地与水系是"不可通行"的边界。

| 走廊 | 走向 | 宽度感 | 地形约束 |
|---|---|---|---|
| 长江水道 | 东→西 | 极窄（田家镇处不足 500 米） | 江面收窄处可封锁 |
| 长江北岸陆路 | 东→西（合肥—六安—潢川—信阳） | 中 | 第 2 军轴线 |
| 长江南岸陆路 | 东→西（安庆—九江—瑞昌—阳新） | 中 | 第 11 军轴线 |
| 大别山北麓 | 东→西（合肥—叶家集—商城—信阳） | 窄（沿山麓） | 富金山、小界岭卡口 |
| 大别山山口 | 北→南（商城—沙窝—麻城） | 极窄 | 沙窝、打店 |
| 南浔线走廊 | 北→南（九江—德安—南昌） | 窄（骑路） | 骑兵沿路布防 |
| 鄱阳湖水路 | 东→西（湖口—姑塘—九江） | — | 姑塘登陆点 |

**用法**：省份生成时，先划走廊，再在走廊上细分省份。走廊内的省邻接度高、通行性好；走廊之间用山地/水域切断。这样生成的地图天然有"轴线感"，而不是均匀的网格。

## A.2 十种战术要点原型

这是最有价值的一条。**不要给每个山头单独写战斗规则，而是定义十种原型，让地图实例化。**

每个地形节点带一个 `prototype` 字段，决定它在战斗解算中的行为。

| 原型 | 几何 | 实例 | 战斗行为 |
|---|---|---|---|
| `ridge_line` 山脊线 | 单条脊线横贯，两侧陡坡不可展开 | 富金山、小界岭、老虎尖 | 正面极窄、纵深极浅，只能硬啃，无法迂回 |
| `river_ridge` 沿江狭长山脊 | 两侧皆水，仅沿脊线机动 | 长山 | 一线天隘路，少兵可久守 |
| `pocket` 背水口袋 | 三面湖沼/江，一面靠山 | 田家镇 | 守方无退路，合围成本低，突围需渡水 |
| `isolated_height` 孤立高地 | 等高线闭合，仅两坡可接近 | 老虎山、朱家山、张古山 | 单轴拉锯，反复易手，攻方无法展开 |
| `village_node` 村落要点 | 道路横穿，房屋密集 | 孔家祠、河洲上、新店 | 被楔入→反冲击的短周期震荡 |
| `road_cut` 公路截断 | 一条公路 + 两侧高地 | 松阳桥、广济公路 | 纵队被横切即分段，可围点打援 |
| `city_gate` 城垣单点突破 | 闭合城墙 + 城门 | 瑞昌（东门） | 一旦破门即全城失守，强攻成本高 |
| `beachhead` 湖岸滩头 | 水面→岸线，点状抗击 | 姑塘、盘塘 | 攻方有水面机动，守方被动 |
| `encircle_gap` 围三缺一 | C 形合围 + 缺口外阻援线 | 万家岭 | 内外双线共享兵力，缺口是双刃剑 |
| `retreat_fan` 多路平行撤退 | 扇形退却路线 | 小界岭转进 | 有序退却而非溃退，损失可控 |

**为什么这个设计好**：它把"历史细节"和"战斗解算"解耦了。加一个新战役不需要写新的战斗逻辑，只需要标注每个要点属于哪个原型。而且玩家能学会识别原型——"这是个背水口袋，我得先撤"——这是真正的策略深度。

## A.3 五种战线变形模式

战斗解算的结果不该只是"推进了 N 公里"，而该是这五种形态之一：

1. **正面平推** — 单向直线推进（潢川、田家镇北面）
2. **钳形合击** — 双翼弧线内收（孔家祠、富金山）
3. **单翼深远迂回** — 一支兵力绕后截断（陈家山 700 人、富金山断后）
4. **横向截断** — 横切公路纵队（松阳桥）
5. **向心合围** — 四方向心收缩（万家岭）

这五种形态可以作为战斗结果的枚举类型，直接驱动前线的可视化。玩家看到的不是数字变化，而是战线形状变化——这才是大战略游戏最爽的反馈。

## A.4 四级图幅

| 层级 | 覆盖 | 显示内容 | 对应省份数 |
|---|---|---|---|
| L1 战略 | 数省 | 军/兵团、走廊、总轴线 | 全图 240-320 |
| L2 战役 | 数十公里 | 师/军、战线弧、要点 | 一个战区 40-60 |
| L3 战术 | 数公里 | 团/营、等高线、工事 | 一个省 + 邻省 |
| L4 战斗 | 数百米 | 连/排、散点、火力线 | 单个地形节点 |

**关键细节**：片中 L3→L4 用的是**同一地点连续推近**，不是跳转。这种连续缩放对玩家的空间认知负担最小，建议沿用。技术上意味着渲染层要支持无缝缩放，不能切换场景。

M2 只需要做到 L2。L3/L4 留到有战术层需求时再说。

## A.5 UI 视觉编码（可直接采用）

视频的视觉语言已经验证过可读性，值得直接借鉴：

| 元素 | 编码 |
|---|---|
| 中方 | 蓝色点阵 / 蓝底标牌 |
| 日军 | 黑色点阵 / 红旗 + 黑底标牌 |
| 战线 | 蓝锯齿弧 |
| 迂回路线 | 虚线弧 |
| 主攻方向 | 粗黑箭头 |
| 工事 | 白色半圆拱 |
| 战果 | 蓝章「夺回/打回/截断」、红章「失守/突破」 |

**兵力密度用点阵密度表达**，相对密度与标注兵力大体一致。这个手法比数字条形图更直观，也天然呈现了"信息模糊"——玩家数不清多少个点。

## A.6 空间数据的缺口（需要在游戏中补）

视频只提供了定性空间关系，以下几项必须由数据管线补：

- 等高线数值（海拔、坡度）→ 用 SRTM
- 比例尺与战线实际长度 → 用投影后的真实坐标
- 道路等级（公路/土路/小径）→ L2 手工标注
- 水系通航性 → 需要额外的航道资料
- 工事等级（野战壕/碉堡/要塞炮台）→ 设计定义
- 指北针与方位 → 投影保证

# 附录 B 从坐标到多边形：前端怎么把省份拼成地图

> 2026-11 落地。解决"只有邻接数据、没有几何形状"的硬缺口。

## B.1 问题

`map.json` 原本只有邻接关系，没有坐标。前端只能画成力导向圆点图——像关系网，不像地图。

## B.2 方案：真实经纬度 + Voronoi 半平面裁剪

**第一步：给每个省一个真实经纬度。**

```json
{ "id": 0, "name": "九江", "lon": 116.00, "lat": 29.71 }
```

这不是随便填的：九江在 116.0E / 29.7N，德安在 115.75E / 29.33N，
南昌在 115.89E / 28.68N。按经纬度摆位置，出来的就是真实的战区走向
（南北 1.1 度、东西 0.8 度，符合南浔线沿铁路南北展开的态势）。

**第二步：投影。**

经度乘中纬度余弦修正（北纬 29° 时约 0.87），避免东西向过度拉伸。
等比缩放后居中放置。

**第三步：Voronoi 裁剪。**

每个省从整个地图矩形开始，依次与**其他所有省**做中垂线半平面裁剪，
只保留靠近自己的一侧。切完就是它的多边形。

```js
function clipHalf(poly, a, b) {
  const mx = (a[0]+b[0])/2, my = (a[1]+b[1])/2;
  const nx = b[0]-a[0], ny = b[1]-a[1];
  // 保留 (p-mid)·n <= 0 的一侧，即靠近 a 的一侧
}
```

这是标准的 Sutherland–Hodgman 裁剪，40 行，无依赖。

## B.3 为什么用 Voronoi 而不是别的

| 方案 | 问题 |
|---|---|
| 画圆圈 | 不是地图，省与省之间有缝 |
| 手画多边形 | 22 个省要画 22 个多边形，200 个省就要画 200 个 |
| 六边形网格 | 形状规整但失去地理感，且需要重构整个地图 |
| **Voronoi** | **从坐标自动生成，无缝，无需手工** |

Voronoi 的额外好处：**多边形边界天然是"到两省等距"的中垂线**，
所以相邻省份共享完全相同的边，永远不会重叠或留缝。

## B.4 实测

22 个省的地图，验证结果：

```
省份数         22
最少顶点数     3
退化多边形     0
总面积/包围盒  100.00%   ← 无缝拼合
```

最小省（箬溪）1315 px²，最大省（永修）46116 px²。

## B.5 已知局限

**省份太少会显得空。** 22 个省摊开在整张纸上，每个多边形很大，
看起来像色块拼图而不是详细地图。

真实战役应该是 **60-100 个省**（南浔线实际控制区约 1 万平方公里，
按每省 100-150 平方公里算）。扩充省份数量是下一步。

**边界是直线的。** Voronoi 生成的边界是数学直线，没有河流、山脊的自然弯曲。
要做出地形感，需要在裁剪后叠加地形约束（比如沿山脊修边），
这属于 `docs/04` 第 6 节的"沿地形线修边"。

## B.6 对模块作者的要求

`map.json` 里给每省填 `lon` / `lat` 即可，其余全自动：

```json
{ "id": 7, "name": "星子", "lon": 116.04, "lat": 29.45 }
```

**不填也能跑**（坐标默认 0,0），但所有省都会叠在左上角——
校验器应该对这种情况报警。这一条还没加。
